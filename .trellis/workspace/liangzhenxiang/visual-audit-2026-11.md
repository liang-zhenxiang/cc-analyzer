# CC Analyzer 产品视觉评审（2026-11）

- 评审对象：`main` @ `c10df4a`（v0.37.0）
- 截图基准：`docs/screenshots/`，1440×900 浅色为主；另抽查 `usage-dark.png`、`gg-seasons-dark.png`
- 方法：截图逐张查看 + 对应组件/CSS/token 代码核对；本次不改任何源码
- 结论：整体视觉语言已经收敛（Panel 同构、tokens 统一、数字层级清楚），
  但存在 1 个**同屏数据互相矛盾**的 P0，以及 6 个影响图表可读性或入口可信度的 P1。
  当前最需要修的不是“再加面板”，而是把已有面板的**口径、刻度和收口**补好。

## 一、问题清单

### P0（先修，影响数据可信度）

#### P0-1 工作日志不受时间区间过滤，与 KPI 行互相矛盾

- **证据**：`usage-light.png` 工作日志区（y≈530–760）。
  - 顶部 KPI：`Tokens 总量 63,050`、`会话数 4`、`近 30 天`。
  - 同一屏工作日志：`10-28` 到 `10-31` 共 8 天，会话数相加为 12，
    token 相加为 309,471；其中 `07-31`、`07-28` 明显不在“近 30 天”内。
  - `usage-below-light.png` 的「会话形状」也按 4 个会话计算，与工作日志的 12 个不一致。
- **代码**：`web/src/features/usage/UsageOverviewPage.tsx:939` 把**全量**
  `inputs` 传给 `StoryLogPanel`；`StoryLogPanel.tsx:37-38` 直接 `storyLog(inputs)`，
  没有窗口裁剪。面板注释写的是“调用方通常先过窗口边界”，但唯一调用方没有过。
  同一页的 `shapeInputs`（`UsageOverviewPage.tsx:289-295`）已经做过正确的窗口裁剪，
  说明这是漏用，不是新需求。
- **为什么影响产品**：同一屏两个数字打架，用户会先怀疑整个产品的统计；
  而且 90 天档在真实每天使用的用户那里会渲染几十行，把趋势图推到更下面。
- **建议**：
  1. 用与 `shapeInputs` 相同的 `startTs` 先裁 `inputs` 再传给 `StoryLogPanel`；
  2. 面板内默认只显示最近 5 天，余下用「展开全部 N 天」按钮；
  3. 脚注补一句「只统计当前时间范围内的开工日」，让口径可见。
- **备注（日期顺序）**：`usage-light.png` / `usage-dark.png` 的日期顺序是
  `10-28 → 10-26 → 10-23 → 07-31 → 07-28 → 11-02 → 11-01 → 10-31`，并非倒序；
  但当前 `storyLog.ts:153-155` 已显式按日期倒序，`gg-story-light.png` 与
  `hh-briefing-light.png` 也都是正确的倒序。两张主题图同序、且与代码不一致，
  更像截图生成时用了旧的 `web/dist` 产物，**归档截图疑似陈旧，需真机/重新出图确认**；
  在确认前不要把“乱序”当成当前代码的确定缺陷，但上面的“区间越界”由代码可独立确认。

### P1（本轮应修，直接影响可读性/入口可信度）

#### P1-1 会话形状卡的 5 个 x 轴标签全部被省略号截断

- **证据**：`ii-shape-light.png` 会话形状卡（y≈330–540）与
  `usage-below-light.png` 同名卡：标签显示为 `不足…`、`5–15…`、`15–6…`、
  `1–4…`、`≥4…`。柱子上方的计数（2/2/3/1/1）清楚，但没人知道柱子对应哪一档。
- **代码**：`SessionShapePanel.module.css:21-27` 的 `.col` 固定
  `width: min(40px, 18%)`；`:47-55` 的 `.label` 是 `overflow:hidden` +
  `text-overflow:ellipsis` + `white-space:nowrap`。原始标签
  （`sessionDurations.ts:39-45`）是「不足 5 分钟 / 5–15 分钟 / 15–60 分钟 /
  1–4 小时 / ≥ 4 小时」，40px 在 11px 字号下只放得下 3 个字左右，必然全截。
- **为什么影响产品**：这张卡的四档视图里，时长分布是最常看的一档；
  标签一断，图表就退化成五个没有含义的色块。
- **建议**：`.col` 改为可伸展（`flex: 1 1 0; min-width: 64px; max-width: 140px`），
  `.label` 允许两行（`white-space: normal; overflow: visible`），
  并在窄窗/130% 下优先保证标签完整；柱子本身不必居中缩在 250px 里。
  若与会话形状并入半宽列（见 P1-3），5×72px + 间距仍放得下。

#### P1-2 计费窗口的「近几个窗口」历史图纵轴标签互相压住

- **证据**：`hh-briefing-light.png` 计费卡右侧（x≈850–1420，y≈250–300）
  的纵轴是 `1M / 800K / 600K / 400K / 200K / 0` 叠在一起；
  `usage-light.png` 同一位置是 `5K / 4K / 3K / 2K / 1K / 0` 压成一团。
  放大后可以确认不是截图模糊，而是文字行距小于字高。
- **代码**：`BillingWindowCard.tsx:411-421` 给 `BarChart` 传 `height={72}`；
  `BarChart.tsx:55` 用 `axisTicks(maxValue, 3)`；`chartPrimitives.tsx:53-60`
  在 max=1M 时返回 6 个刻度（0…1M），而绘图区高度只有
  `72 - 8 - 22 = 42px`，6 个 11px 标签平均 8.4px 一个，必然重叠。
  130% 字号下刻度字放大到约 14px，间距不变，重叠更严重。
- **为什么影响产品**：这是首屏计费卡的一部分，看起来像渲染坏了；
  用户无法判断柱子的高度量级，而这张图本来是用来读“窗口消耗在涨还是在降”的。
- **建议**：让刻度数随绘图区高度决定，而不是固定 3：
  `steps = clamp(1, floor(plotHeight / 16), 3)`，或 `height ≤ 96` 时只保留
  0 与 max 两个刻度；同时把 `height` 提到 96–104，给标签留出行高。
  `DailyTrendChart` 的 `height={170}` 不受影响，改动只落在短图分支。

#### P1-3 「活跃时段」卡独占半行，右侧整块空白

- **证据**：`ii-shape-light.png` 顶部「活跃时段（周 × 小时）」卡宽约 713px，
  右侧 715px 全空；`usage-below-light.png` 顶部同样。它下面紧接着的
  「会话形状」却是整行。
- **代码**：`UsageOverviewPage.tsx:1102-1118` 的活跃时段 `Panel` 是
  `.board` 两列网格的直接子项；它前一个区块是整行 `compactionRow`（流向图），
  后一个区块也是整行 `compactionRow`（会话形状），所以它只能占第一列。
  `.board` 的 `grid-template-columns: repeat(2, minmax(0, 1fr))`
  见 `UsageOverviewPage.module.css:135-140`。
- **为什么影响产品**：一屏里白白浪费一半宽度，页面因此更长；
  而且热力图本身只有 7×24 格，半宽其实刚好，另一半本可以放同一维度的“会话形状”。
- **建议**：把「会话形状」从整行 `compactionRow` 移出来，与「活跃时段」
  并排成一对（两者都是“活动/会话的形状”）；窄窗（≤1080px）再各自整行。
  这是 JSX 顺序 + 一个类名的小改动，不需要新组件。若不想配对，至少给活跃时段
  加 `grid-column: 1 / -1`，并把热力图在卡内居中，避免左侧贴边、右侧空洞。

#### P1-4 项目卡片是可点击按钮但点击无动作；季节条用分类色表达季度且只显示最大值

- **证据**：`gg-seasons-light.png` 项目卡片区（y≈320–520）。卡片有 hover 底色、
  `cursor:pointer` 的按钮语义，但点击没有任何跳转；季节条是蓝/青/绿/琥珀四色，
  文字只写「Q4 最重（64%）」「Q4 最重（44%）」，另外三季的占比不可见。
- **代码**：
  - `ProjectCardsPanel.tsx:150-159` 渲染 `<button>`，`onClick={() => onOpenProject?.(...)}`；
    `title` 写「项目筛选视图将在后续版本提供」；而唯一调用方
    `UsageOverviewPage.tsx:983` 没有传 `onOpenProject`，所以点击必然什么都不发生。
  - `ProjectCardsPanel.module.css:142-159` 用 `--chart-1..4` 给 Q1–Q4 上色；
    `tokens.css:91-95` 明确写着「图表色板严禁借给日期维度」，
    而季度正是日期维度。Q4 用的 `--chart-4`（#a67a08）又和 `--warning`（#946200）
    几乎同色，读起来像“Q4 有风险”。
  - `ProjectCardsPanel.tsx:50-58` 的 `seasonText` 只拼“最重季 + 空季”，
    四段百分比只存在于 `aria-label`（`seasonAria`，`:61-63`），视觉用户看不到。
- **为什么影响产品**：死按钮会消耗一次点击信任；四色让用户在“四个类别”和
  “四个时间阶段”之间误读；只显示最大值等于把一张四段图压缩成了一个数字。
- **建议**：
  1. 在 `onOpenProject` 缺省时渲染为静态 `div`/`article`，去掉 hover 与按钮语义，
     或加一个明确的「即将支持」小徽标（但不要保留可点外观）；
  2. 季节条改成**单色相 4 级明度阶**（新增 4 个 ordinal token，或复用一套
     已为“顺序”设计的 ramp），不要用 `--chart-*`；若暂不加 token，可先用
     `--text-tertiary` 的四档中性灰，把“最重季”用 `--accent` 单独强调；
  3. 把四段占比写成一行可见文本：`Q1 18% · Q2 12% · Q3 6% · Q4 64%`，
     6px 条只负责形状，文字负责读数。

#### P1-5 会话时间线在短会话下四个轴标签全是同一个时刻

- **证据**：`analyzer-log-light.png` 顶部时间轨道（y≈150–200），
  左、1/3、2/3、右四个刻度全是 `18:00`；而这条会话总耗时只有 `8.00s`。
- **代码**：`TimelineTrack.tsx:164-167` 四处都用 `formatClock(ts)`；
  `format.ts:54` 的 `formatClock` 默认只到 `HH:mm`，只有探针气泡
  （`TimelineTrack.tsx:96`）用了 `formatClock(at, true)`。所以 8 秒的会话，
  四个刻度必然同字。
- **为什么影响产品**：时间轨道是会话页的第一张图，轴没有区分度，
  用户无法判断蓝块在会话的哪个位置，也无法用刻度辅助框选。
- **建议**：按跨度选精度：`span < 10 分钟` 用 `HH:mm:ss`；
  `span < 60 秒` 用相对秒数（`0s / 2s / 4s / 8s`）或 `mm:ss`。
  探针气泡已经是秒级，轴标签跟上即可。改动只在 `TimelineTrack.tsx` 的一个
  formatter，风险很低。

#### P1-6 计费窗口“已关闭”后仍显示「预计到达限额」与「若保持此速率」

- **证据**：`hh-briefing-light.png` 计费卡左侧：
  「窗口关闭 已关闭 19:10」同时显示「预计到达限额 11-03 22:19」，
  下面还有「若保持此速率：预计用到限额的 10% · 安静」。
  窗口已经关闭，22:19 的触顶预测没有意义。
- **代码**：`billingWindow.ts:62-72` 的 `currentBlock` 明确“最新块即使
  `now` 已过结束也返回”，这是为了保留“那个窗口消耗了多少”的事实；
  但 `predictLimitReach`（`billingWindow.ts:109-123`）与 `buildLimitForecast`
  （`limitForecast.ts:49-87`）没有对 `now > block.end` 做收口，
  于是用已关闭窗口的均值继续外推。
- **为什么影响产品**：同一张卡里“已关闭”和“未来 22:19 触顶”互相矛盾，
  会让用户怀疑所有“推算”徽章；这属于数据表达错误，不只是文案问题。
- **建议**：`closesIn <= 0` 时：
  - 「预计到达限额」显示 `窗口已关闭`（不再给时间）；
  - 隐藏「若保持此速率」整行，或改成「窗口已关闭，等待下一窗口」；
  - 保留表盘、已用、滚动 7 天这些事实读数。
  改动集中在 `BillingWindowCard.tsx:315-353` + 模型层守卫 + 对应测试。

## 三、建议本轮修复的 5 条（按推荐顺序）

### 1. 工作日志按所选区间过滤，并默认只显示 5 天（P0-1）

  首屏重新收回到“计费 + KPI + 最近几天”的节奏。这是本轮唯一 P0。

## 四、960px / 130% / 深色 / 高对比度推断

### 960px

- `.board` 的断点是 **900px**（`UsageOverviewPage.module.css:192-208`），
  所以 960px 仍是两列：活跃时段的“半行空白”会保留；计费卡
  `.gaugeArea` 会把 `sideStack` 挤到第二行，历史图被拉宽，**P1-2 的刻度重叠更明显**。
- 工作日志、KPI 四列、项目卡片网格在 960px 都不会横向溢出，但 KPI 脚注
  会从 1 行变 2–3 行，首屏进一步变高。
- 会话页顶栏：`SessionHeader.module.css:228-232` 在 ≤1280px 直接隐藏
  `healthNote`，只剩分数；`titleRow` 的 `flex-wrap` 会让 4 个动作按钮换行，
  表格可用高度减少。**需真机确认**换行后的首屏是否仍守住“表格内部滚动”的不变量。
- 设置抽屉 415px 在 960px 下占 43%，可接受；字号五档按钮仍放得下。

### 130% 字号

- `SessionShapePanel` 的 40px 列是**固定 px**，标签字号从 11px 变 14.3px，
  截断更严重（P1-1）。
- `BarChart` 的 `height=72` 是**固定 px**，刻度字号却随 `--font-scale` 放大，
  6 个刻度在 42px 绘图区里重叠更严重（P1-2）。
- `SessionHeader` 的 `.readouts` 是 `flex-wrap: nowrap`（`SessionHeader.module.css:112-120`），
  五个读数在 130% 下是否还放得下，**需真机确认**；如果溢出，会直接破横向。
- 实验室 `.grid` 在 ≤1080px 已全部单列，130% 下只会更长，不会断；
  但星系/热力图的 SVG 文字会随字号变大，可能压到相邻刻度。

### 深色 / 高对比度

- 抽查 `usage-dark.png`、`gg-seasons-dark.png`：P1-2 的刻度重叠、
  P1-1 的标签截断、P1-3 的半行空白在深色下**同样存在**（几何问题与主题无关）。
- 季节条的 `-soft` + 1px 描边在深色下仍能读出四段，但四色的语义混用不变；
  Q4 琥珀与 `--warning` 在深色下更接近（`#edc14e` vs `#e0a33e`）。
- 高对比度下 tokens 会把 `-soft` 换成实色，季节条反而更清楚；
  但本次没有 HC 截图，**建议真机确认** HC 下 6px 高的四段条是否还能分辨边界。

## 六、一句话结论

**先修工作日志的区间口径（P0-1）**：它是唯一会让人不相信整页数字的问题，
而且和“日志太长”“首屏被推下去”“07 月日期越界”是同一个根因。
修完它，再按“计费卡刻度/预测 → 会话形状标签 → 活跃时段配对 → 项目卡片”
的顺序做四个小步，本轮就能把用量页从“功能很多”提升到“第一屏可信、图表可读”。
