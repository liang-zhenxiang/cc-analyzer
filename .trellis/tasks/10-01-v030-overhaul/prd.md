## 背景

CC Analyzer 目前功能已经能跑（v0.2.2），开源基建也已就位（CI、治理文件、
发布流水线全部可用）。但它还停在「一个能用的工具」的阶段，离「一个别人愿意
用、愿意贡献的项目」还差三件事：

1. **没有测试网**。前端有一批 Vitest 用例，但没有任何端到端测试，
   更没有真正打开应用验证的 GUI 测试。结果是：**每一次改动都不知道有没有
   碰坏旧功能**——这直接压制了迭代速度，也吓退了潜在贡献者。
2. **界面只是「能用」，不是「想用」**。对一个要被反复打开的桌面工具来说，
   美观度不是锦上添花，它决定了用户第一次打开会不会留下来。
3. **不知道自己相对于同类工具处在什么位置**。闭门造车容易做出「自我感觉
   良好但没人需要」的功能。

同时，项目此前把开发规范放在 `AGENTS.md` 与 skill 里，**需求探索的过程不落盘**——
会话一压缩，取舍和调研就没了。这一版引入 Trellis 工程框架来补上这一层。

## 期望

分三条并行的子任务线，**每条线独立可验证、独立可合并**：

| 子任务 | 目录 | 交付什么 |
| --- | --- | --- |
| 测试体系 | `.trellis/tasks/10-01-testing-infra/` | 单元 / 端到端 / 真实 GUI 截图三层测试，全部接入 CI |
| UI/UX 精品化 | `.trellis/tasks/10-01-ui-ux-overhaul/` | 由专业设计方向产出的视觉方案 + 真机截图逐屏验证 |
| 竞品对齐 | `.trellis/tasks/10-01-feature-parity/` | 同类工具调研结论 + 高价值功能的融合落地 |

贯穿三条线的**工作方式要求**（来自维护者，见下方原文）：

- 全自动完成，不要中途提问
- **小批量提交，功能闭环就提交**，不要堆积到一个大功能点才提交
- 所有需求与结论**沉淀进 Trellis**，避免以后忘记

## 验收标准

- [ ] 三层测试在本地与 CI 都能跑，且**新增功能会被要求补测试**
- [ ] GUI 测试**真实启动应用**并产出截图证据
- [ ] 视觉方案落地后有**真机截图**佐证（不是「我觉得好看了」）
- [ ] 竞品调研有**可追溯的来源**，借鉴点写明改造成什么样子
- [ ] 每个功能闭环各自成 PR，**不攒大提交**
- [ ] 全部需求可从本文件与三个子任务的 PRD 复原

## 非目标

- 不追求功能数量。**「好用、想用」优先于「功能多」**——维护者原话：
  「首先界面美观度必须是第一位的，然后好用，想用」
- 不做照抄式对标。借鉴必须经过融合改造，无缝并入现有信息架构
- 不引入任何把会话数据送出本机的机制（项目红线，见 `AGENTS.md`）
