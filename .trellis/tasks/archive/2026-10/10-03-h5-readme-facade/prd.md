# PRD：README 门面补全

> 对应 Round H 子任务 5 · 创建于 2026-10-03
> 发现方式：维护者审「潜在用户第一眼看到的东西」——README 是本项目最重要的一页

## 背景

本轮的目标是「吸引更多人来用」。README 是唯一一个**所有人都会看**的页面，
而它现在**在卖三四个版本前的产品**。

落地页没有。

## 用户故事

- 作为**第一次看到这个仓库的人**，我在 30 秒内应当知道：它是什么、比别人多什么、
  怎么装。现在我在功能清单里看不到它最独特的那个能力。
- 作为**已经在用同类 CLI 工具的人**，我想知道换过来能得到什么——计费窗口与
  计划感知正是他们抱怨最多、而这里做得最认真的部分。
- 作为**贡献者**，我照 README 的「推送前的检查」跑一遍，应当跑全 CI 会跑的层。

## 功能需求

1. **功能清单补齐**：按 `docs/USAGE.md` 与 `CHANGELOG.md` 的实际交付补全——
   至少包含 5 小时计费窗口与订阅计划感知、全局搜索、双渠道自动更新、
   首屏读数行、复制 resume 命令。措辞面向「能做什么」，不写实现细节。
2. **计费窗口提到显眼位置**：它是本项目对外最强的差异点，不应埋在功能清单中段。
   给一段「它解决什么问题」的短说明（订阅用户每天看几十次的数字：窗口何时关、
   还剩多少、按当前速度何时触顶）。
3. **首图描述与实际画面相符**：`usage-light.png` 的 alt 与正文补上计费窗口卡片。
4. **路线图改写**：删掉已完成的条目，换成真实的开放项（可链接到对应 Issue）。
   路线图是承诺，把做完的事挂在待办里等于告诉访客「这个项目落后了」。
5. **「推送前的检查」与 `AGENTS.md` 对齐**：补上端到端与真机 GUI 两层。
   （若两处内容重复，遵守仓库既有规矩：**同一主题只允许有一个权威位置**——
   把清单留在 README 并指向 `AGENTS.md`，或反过来，不要各写一份。）
6. **中英双语同步**：两版结构与内容一致（仓库已声明「两份 README 结构一致」）。
7. **尽可能加自动检查**：让「两版 README 结构不一致」「README 引用的文档不存在」
   变成可判定的失败，而不是靠人记得同步。若判断成本高于收益，在 PR 里说明理由
   并至少给出人工核对结论。

## 约束

- **不改既有声明中的事实**：许可证、平台、隐私立场、产物命名等一律不动；
  本轮只补「已经做出来但没写出来」的东西。
- **不夸大**：每条能力都要能在代码或 `CHANGELOG.md` 里找到依据。禁止写
  「最强大」「第一名」这类不可验证的话。
- **不写竞品对比表**：本项目先前刻意没有做竞品对标文案。若确要提一句差异，
  必须是**可核实的技术事实**（例如「窗口口径与 ccusage 的 blocks 一致」——
  这句 USAGE.md 已有），且措辞克制。**默认不做对比表**。
- 图片路径沿用 `docs/screenshots/`，且必须通过 `./scripts/check-screenshots.sh`。
- 两版 README 的行数差异不需要消失，但**章节顺序必须一致**。

## 非目标

- 不重写 README 的整体结构或视觉风格。
- 不改 `docs/USAGE.md` / `docs/ARCHITECTURE.md` 的正文（它们是最新的）。
- 不做官网、不做 GIF 演示（那需要额外的截图/录屏流水线，另议）。

## 验收标准

- [ ] 两版 README 的功能清单都包含计费窗口、全局搜索、双渠道更新、读数行、复制 resume 命令
- [ ] 计费窗口有独立的短说明段，而不只是清单里的一行
- [ ] `usage-light.png` 的 alt 与正文都与画面一致（含计费窗口）
- [ ] 路线图无已完成条目；开放项与真实 Issue 对应
- [ ] 「推送前的检查」包含 e2e 与真机 GUI，且与 `AGENTS.md` 的权威位置不冲突
- [ ] 两版 README 章节顺序一致（附人工核对结论，或新增的自动检查输出）
- [ ] 每条新增能力都能在 `CHANGELOG.md` 或代码中找到依据（PR 里给出对应关系）
- [ ] `./scripts/check-screenshots.sh` 与 `./scripts/lint.sh` 全绿
