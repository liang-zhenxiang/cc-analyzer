# Round I 设计评审 · CC Analyzer

> 评审人：UI/UX 设计评审（子 agent）｜日期：2026-10-07｜基线：`ff47a48`（v0.13.0-beta.1）
> 方法：**亲眼看图 + DOM 实测**。归档截图 `SCREENSHOTS=1 npm --prefix web run test:e2e -- screenshots.spec.ts`
> （light/dark × chromium/webkit，产物 `docs/screenshots/`），另补拍搜索浮层 / 导出浮层 /
> 错误态 / 空数据，并在 `deviceScaleFactor: 3` 下对关键区域做放大裁切。
> 所有涉及像素与颜色的结论都来自 `getBoundingClientRect` / `getComputedStyle` 实测，
> 不来自截图目测——本文末尾「已否证的猜想」列出 8 条目测错误。

## 0. 结论摘要

设计语言（`tokens.css` 的「仪器面板」方向 A）是**站得住的**：四级表面台阶 + 发丝边框、
类别色与图表色两套资产互不借用、强调色像素占比 < 3%、字号与行高成对缩放——
这些规则本身比多数同类项目干净。问题不在语言，在**几处「语言没有被执行到」**的地方：

1. **语义最强的位置没有语义色**：失败记录与正常记录的区别只有 12px 字重 400→600，
   而且失败行被涂成蓝色（`--cat-direct`，与「工具」类同色）。
2. **三种「未完成」被直接暴露给用户**：ANSI 转义序列当正文渲染、开发者调试文案
   （连夹具说明一起）进 UI、绝对路径进 UI。
3. **表格的列预算错了**：129px 给了一列读不出来的 waterfall，而摘要列在 305px 处截断；
   且筛选一次整表列宽重排（时间列 +30px，摘要列 −117px）。
4. **用量总览的首屏不成立**：内容 1492px 塞进 852px 的 `main`，仪表盘最关键的三块
   （按项目分布 / 按模型分布 / 活跃时段 7×24）**默认在视野之外**，
   所以仓库里的归档截图从来没有拍到过它们。

## 1. 逐屏评审

### 1.1 会话分析 · 空态（`analyzer-empty-{light,dark}`）

- **视觉层级**：正确。品牌图标 → 「选择一个会话开始分析」→ 一句引导，三级清楚。
- **对齐**：空态在右栏（328–1428）内水平居中于 878，与页面几何一致；
  但它占的是一块 1100×740 的空场，只有 48px 的图标和两行字。属于「空得没有设计」，
  而不是「密度失控」。可接受，但**同一套 EmptyState 在错误路径上会出事**，见 3.1-3。
- **色彩**：`--text-secondary` 的引导句（约 4.5:1 以上）没问题；图标是 48px 的 PNG
  品牌方章，浅色下略像应用商店角标，建议改用 `BrandMark` 内联 SVG 或降饱和度。
- **字体**：引导句 `--fs-base`(13px)，标题 `--fs-lg`(20px)/600。**两者与全站其它
  「标题」共用同一档**，没有为「空态标题」单独留级——可以接受。

### 1.2 会话分析 · 日志视图（`analyzer-log-{light,dark}`）

第一眼看到的是**黑色主按钮「生成整会话分析」**（`analyzer-log-light` 中唯一的高对比块），
第二眼才是会话标题。应该第一眼看的是**会话标识与它的读数**（这是仪器面板的「表头」。
标题与 5 个指标值**同为 15px/600**（实测 `8.00s`、`50`、`0`、`30`、`4` 全部
`fs 15px fw 600`，与 `.sessionTitle` 同级），所以头部没有唯一焦点。

- **会话读数条**：组内 4px、组间 16px 的间距实测成立，分组是清楚的——
  我先前以为「读起来连成一句」是目测偏差，已否证。
- **时间轴（scrubber）是本屏最弱的一块**，具体三处：
  1. **四个刻度标签完全相同，都是 `18:00`**（实测四个 text 的 `textContent` 全为 `18:00`，
     位置 341 / 684 / 1041 / 1389）。会话只有几秒，而 formatter 用 HH:MM。
     一条**完全没有信息量**的坐标轴 = 「看起来坏掉」。
  2. **网格线间距不均**（放大裁切 `zoom/scrubber-light.png` 目测约 150/148/80/192/250/
     142/146/142/148/72/138/122/180）。若轴为「压缩空档的时间轴」是合理的，
     但界面上**没有任何地方说明轴是非线性的**。
  3. **一个孤零零的实心蓝块**（实测约 154×41，位于 746–900，纵向只占轨道 69px 中的 41px
     且贴顶），无标签、无 tooltip；轨道左端还有一条 3px 的粉红竖线（`#c96` 系，
     全站别处未出现该色），无图例无说明。蓝色实心块是全站唯一的「un-soft 大填充」，
     与 `tokens.css` 里「大面积填充只允许 -soft」的规则相冲突。
- **筛选栏**：三组 `<fieldset><legend>` 的「缺口描边」是表单式语汇，与「仪器面板」的
  发丝边框 + 台阶语汇不同源；三组之间的间隙实测约 12px 与 9px **不相等**；
  chip 高 24px（`--control-h-sm`），同一行的输入框/下拉是 28px（`--control-h`），
  **同一行差 4px**，垂直基线不齐（`zoom/filterbar-light.png` 可见）。
- **表格**（本节主要问题，详见 3.1-4 列预算 与 3.1-1 失败语义色）：
  - 表头 `waterfall` 是**全表唯一一个英文词**，其余 8 列都是中文。
  - 行高实测 **38 / 37 / 36** 三种（同一张表内）。
  - 类型 chip 与「时间」单元格各有一条类别色竖条，**同一行出现两次同义色条**。
  - `占比` 列 148px：条 56px + 11px 的三级灰数字；`waterfall` 列 129px：10px 高的条。
  - 摘要列 305px，第三行被截到「…我跑…」。
- **报告面板**：空态是一个大空盒子 + 居中一句「选择报告范围后点击生成。」；
  主按钮「生成整会话分析」与选中 tab「整会话分析」**在同一行重复同一句话**；
  分段控件里「节点分析」比「筛选后分析 / 时间块分析」更淡，
  说明同一控件里存在**选中 / 未选中 / 禁用三态，而只靠灰度区分**。

### 1.3 会话分析 · 树视图（`analyzer-tree-{light,dark}`）

- **这是全站信息层级做得最好的一屏**：图例（等用户/直接工具/委派 Agent/workflow/
  LLM 计算）用 Okabe-Ito 类别色方块，缩进 + 次数/耗时/占比三列右对齐（实测右缘
  100%/0%/38% 全部对齐在 1047）+ 占比条统一从 1058 起。可以不动。
- **唯一的硬伤**：卡片底部裁到**半行**（`workflow` 行在 y≈715 处被卡片下边缘腰斩），
  没有淡出遮罩、没有滚动提示。容器高度不是行高的整数倍导致的，属于「看起来没做完」。
- 「定位日志」是 hover 才出现的按钮，且**盖在占比条上**——同一个像素区域既是
  数据条又是点击目标，命中语义冲突。

### 1.4 会话分析 · 报告视图（`analyzer-report-{light,dark}`）

- **垂直预算分配错误**：时间轴卡（≈140px）与筛选卡（≈122px）占了首屏最好的位置，
  而报告面板（高价值产出）从 y=730 起、只剩 170px 可视，正文溢出到视口外。
  一屏之内「输入区占 260px，产出区占 170px」是反的。
- 报告正文极度稀疏：4 行字占 250px 高的带边框盒子，右侧 40% 全空。
- 数据自相矛盾（夹具）：「总耗时 8.00s」与报告里「总时长: 3 分 12 秒」并置，
  没有任何文字说明两者口径不同（墙钟 vs 耗时求和）。
- 空态提示实测 13px / `#16181b`（**主文字色**），比面板标题还实——提示抢了标题的位置。
- 深色下主按钮反转为白底黑字（与浅色黑底白字对称），这是**做对的地方**，勿改。

### 1.5 用量总览（`usage-{light,dark}`）

**首屏不成立**：`main` 实测 `scrollHeight 1492 / clientHeight 852`，即
**仪表盘 43% 的内容在默认视野之外**，其中包含三块独立面板：
「按项目分布」「按模型分布」「活跃时段（7×24）」。归档截图（900px 视口、不滚动）
因此**从来没有拍到过它们**——`docs/screenshots/usage-*.png` 是残缺的。

- **环形图**：一张 200px 的空心圆环（`stroke` 约 14px），因为没有订阅计划，
  进度弧为 0，**整块纯装饰**，却占了本页最大的一块黄金位置（实测卡 350.8px 高）。
  旁边 4 个指标的排布更错：
  - 「消耗 / 速度」标签换行成两行（其余三个标签一行），导致该指标**基线不齐**。
  - 四个指标用 flex 排布而非网格，label→value 间距实测 92 / 54 / 53 / 103px，
    **不等距**。
  - 「按消耗速度推算」的琥珀 chip 比它标注的数值（`13,640/时`）还宽，**注解比数据响**。
  - 「未选计划」是「无数据」的占位，却用 15px/600 与其它真值同权重。
- **`读自日志` 出现 5 次**（窗口开启/窗口关闭/消耗/Tokens 总量/会话数/消息数），
  绿色实底 + 绿字 + 绿边框的小胶囊，**是本页出现次数最多、最抢眼的彩色元素**，
  而它标注的是同一句话：数据来自日志。信息量≈0，视觉权重≈最高。
- **KPI 条**：「会话数 2 [读自日志]」里 chip 比数字宽 3 倍——**层级倒置**。
  第四列「估算成本 · 非账单 / $0.26 / 按定价快照估算 快照日期 2026-10-01」
  一个数字配了**三层免责声明**（列头「非账单」+ chip「估算」+「快照」），
  且这一列的第二个 chip 决定了整条 KPI 卡的高度，**前三列各留 60px 死白**。
- **近几个窗口**：Y 轴刻度实测 320.4 / 349.1 / 377.7 / 406.3（等距 28.6），
  标签右缘全部 276.5——**轴做得正确**（我先前目测「不等距」是错的）。
  问题在数据侧：6 根柱里 **3 根高 0**（实测 `h=0/0.1/0`），
  所以图表 90% 是空的；可见的 3 根柱宽 51.5、间距 156，**柱间距是柱宽的 2 倍**。
  X 轴是「等距排布但时间间隔不等」（08:00→11:04→18:00→18:00→18:05→18:15
  = 3h/7h/0h/5m/10m），看起来像时间轴其实不是。
- **每日 Token 消耗**：X 轴标签是 `9-8 / 9-11 / … / 10-5`——**裸 M-D**，
  无年份、与另一图的 `HH:MM` 体例混用，且 30 个槽位里只有最后 5 天有数据，
  左侧 85% 空场。柱同样是 10% 填充 + 1px 描边，**在浅色下几乎只剩描边**，
  看不出「面积」，柱高比较变得困难。
- **按项目分布 / 按模型分布**：两张并排卡**高度不等**（实测 107.3 vs 160.7），
  左边那张下方空出 54px；类别标签是**原始目录名** `-repo-usage-days`；
  模型图例是**原始 model id** `claude-sonnet-4-5-20250929`（三者共享 `claude-` 前缀，
  差异在末尾，最不利的标签结构）。堆叠条的比例是对的（88%/7.1%/4.5% 对 85.6%/8.6%/5.9%）。
- **活跃时段（7×24）**：168 个格子**同时有填充和描边**（空/非空双重编码），
  且**没有色阶图例**——热力图没有图例等于没有刻度。标题里的 `(7×24)` 是规格不是标签。
- **容器宽度**：用量页是居中 1080px（卡 192–1248，两侧各 180px 死边），
  而分析页是全幅 12–1428。**切 tab 时内容整体横跳 168px**。

### 1.6 实时监控（`monitor-{light,dark}`）

全站最弱的一屏。1440×844 的空场里只有一个 300×150 的孤岛：
48px 图标 + 「实时监控未打开」+ 一行灰字 + 一个按钮。

- 描述文案是**写给维护者看的**：「打开后会内嵌本机 localhost 上运行的监控仪表盘。
  **该服务不在本仓库内，需要另行启动。**」终端用户读到「需要另行启动」就结束了。
- **没有端口号、没有 URL、没有重试、没有文档链接**，也没有「怎么启动」的一步说明。
- 定位：空态在页面垂直居中（与空态/监控一致），但**用量页的错误态却是顶部对齐**——
  同一套语义三种位置（见 1.10）。

### 1.7 设置抽屉（`settings-{light,dark}`，`zoom/drawer-{top,mid}-light.png`）

- 抽屉不透明、z-index 20、420px 宽、内容 16px 内边距，**几何是干净的**。
  面板顶部「12:04:08 · LLM · claude-sonnet-4 · 3.00s / 提示词 17 / 输出 34 · 2.7% · 正常」
  是 `ThresholdsPanel.tsx:235` **有意做的字号实时预览行**（跟着 `--font-scale` 缩放），
  这是**做得好的一处**，别误删。
- **问题：9 个同级 section 排成一列平铺**（界面字号 / Prompt 上限 / 记录明细行数 /
  最慢工具条数 / 子 agent 条数 / 解析分块行数 / 列表窗口行数 / 计费窗口 / 订阅计划 / 更新 / 归档），
  没有分组标题也没有分隔线，用户找「计费窗口」必须逐个读标题。
- **同一抽屉内两种字段排布**：「界面字号」是 标题 → 说明 → 控件；
  其余全部是 标题 → 控件 → 说明。同一形式两种顺序，属于规则漂移。
- 输入框（120px、`--bg-inset` 底、radius 6）与单位（KB/条/行）右缘对齐在 1147，
  **做对了**。
- 无遮罩（与导出浮层不一致，见 1.9）。

### 1.8 全局搜索浮层（`zoom/search-{light,dark}.png`，`.trellis/tasks/round-i-shots/search-*.png`）

- **P0：ANSI 转义序列当正文渲染。** 命中行显示
  `[33m构建失败[0m: 先修 src/app.ts:12。`——用户直接看到 `[33m` / `[0m`。
  日志视图走了 `AnsiText`，搜索浮层没有。
- **浮层没有遮罩**（`SearchPalette` 是 `aria-modal` 的对话框，页面却全亮），
  而导出浮层**有**遮罩。两个对话框两种语言。
- **`1-3` 无标签、无解释**，三条命中都是 `1-3`，位置在行尾且与被搜索词无关的视觉权重。
- 命中词**没有被高亮**（`<mark>` 之类），只靠行底色区分选中行；
  选中行的文字被染成强调蓝（在深色下是浅蓝底 + 浅蓝字），**对比度下降**。
- 分组标题是 `-repo-ansi` 原始目录名；空态里 hint「输入关键词搜索全部会话的消息」
  与 placeholder「搜索全部项目的会话消息…（Esc 关闭）」**几乎同义**，两行说一件事。
- 空态高度只有约 59px（输入框 + 一行提示），没有任何键盘图例
  （↑↓ / Enter / Esc）、没有「搜索范围」说明——命令面板的惯例资产全缺。

### 1.9 导出浮层（`zoom/export-light.png`）

**这是全站完成度最高的浮层**：12px 圆角（`--r-lg`，符合「浮层专用」的 token 分工）、
有遮罩、16px 内边距、分段控件两段等宽（446/2=221 实测）、
选中段白底 + 描边 + 600 字重（三信号，清晰）、信息块 `--bg-inset` 底、
文件名用 `--font-mono`（**好细节**）、footer 次/主按钮顺序正确。

- 小问题：文件名 `cc-analyzer-3d2a5442-filtered.html` 里带 `filtered`，
  而上方信息块明说「当前没有生效的筛选，两个范围内容相同」——**文件名自相矛盾**。
- 「文件名 ___」是 label + 空格 + 值，没有分隔符，读起来像一句话。
- 会话 id 只留 8 位，用户无法确认是哪个会话。
- 纵向留白偏大（两个分段控件 + 3 行字撑到 478×370），
  与「密集/仪器」语言相比偏松，但不算缺陷。

### 1.10 错误态（意外收获：`nodata-*.png`）

用「声明的路径不存在」触发了真实错误路径，暴露出**三种互不一致的错误呈现**：

1. **侧栏内联**：粉色底 + 红字 + 4 行，内容是
   `扫描会话列表失败: Error: E2E 虚拟文件系统: readDir 遇到未声明的路径
   /Users/e2e/.claude/projects。请在夹具里声明它——静默返回空数组会把夹具错误伪装成成功缺陷。`
   ——**夹具说明进了用户界面**，并带绝对用户路径。同一屏下面还同时显示
   「没有匹配的会话 / 调整搜索词后重试。」——**错误与「没有匹配」自相矛盾**，
   且后者的建议完全错。
2. **用量页整页**：图标 + 「会话列表读取失败」+ **一整行横跨约 1000px 的 12px 灰字**
   （远超可读行长），**顶部对齐**（与其它空态的居中不一致），**无重试、无退出**。
3. **监控页**：居中、有按钮、可操作——**这一种是对的**。

### 1.11 深色主题专项

- 表面台阶、发丝边框、类别色、图表色在深色下都成立；主按钮白/黑反转正确；
  卡片与页面底色对比足够。`--text` `#f0f2f5`、`--text-tertiary` `#8b939e` 实测可读。
- 具体问题：**「近 7 天 / 近 90 天」未选中 chip 在深色下几乎没有边框与底色**
  （浅色下也淡），只有选中态可辨——与筛选 chip（`--bg-inset` 底 + 描边）不是同一套。
- 深色下**琥珀 chip 是全卡最亮的元素**（`--warning` 系描边 + 透明底），
  比它标注的数据亮，语义色被当装饰用了。
- `占比` 条的轨道在深色下是 `rgba(16,24,40,0.18)`——在深底上几乎不可见，
  只剩下染色的一段。轨道应在深色下换成亮一档的 token。

## 2. 方法论上的一处缺口（建议顺手补）

`web/e2e/screenshots.spec.ts` 用 900px 视口、不滚动，而用量页的滚动在 `main` 内部
（`overflow: auto`，`scrollHeight 1492`）。结果是**归档截图长期只覆盖页面的前 57%**，
`按项目分布 / 按模型分布 / 活跃时段` 三块从未进入 `docs/screenshots/`，

`main.scrollTop = main.scrollHeight` 后再补一张，或给仪表盘加 `-bottom` 视图名。
**这一条不是设计缺陷，但它让「看截图验收」这件事对用量页失效——比任何单点缺陷更值得修。**

**3. 错误态重做（三种形态 → 一种）**
- 问题：见 1.10。开发者文案 + 夹具说明 + 绝对路径进 UI；错误态与「没有匹配」同屏

### 3.2 P1 —— 明显拖后腿，值得进本轮

**5. Y 轴刻度不是「整齐的数」（一行修复，两张图受益）**
- 问题：`chartPrimitives.tsx:28` 的 `axisTicks(max, steps = 3)` 是
  `max * index / steps`——**把轴最大值等分 3 份**，没有「取整齐数」这一步。
  于是 200K 的轴刻出 0 / 66,666 / 133,333 / 200,000，经
  `formatAxisValue` 的 compact formatter 渲染成 **`0 / 66.7K / 133.3K / 200K`**。
  实测轴几何是对的（320.4/349.1/377.7/406.3，等距 28.6，标签右缘统一 276.5），
  所以问题**只在刻度取值**：`66.7K` / `133.3K` 是「等分 3 份」的指纹，
  一眼就能看出坐标轴是自动生成的，而不是仪器上校过的。
- 为什么：坐标轴的刻度必须落在 1/2/5×10ⁿ 上（读者才能心算、才能跨图比较）；
  等分数值逼着用户做除法。这是图表「专业 vs 自动生成」最直接的分界线，
  而且它是**唯一一处改一个函数就同时修好两张图**的地方。
- 怎么改：把 `axisTicks` 换成 nice-number 步长——`raw = max / steps`，
  `step = 10^floor(log10(raw)) × {1,2,5,10}` 取最小的使 `max/step ≤ steps` 的那档，
  再从 0 按 step 铺到 ≥ max。200K → 步长 50K → `0 / 50K / 100K / 150K / 200K`。
  `formatAxisValue` 不动。补一条单测（`chartPrimitives` 是纯函数，好测）。
- 影响面：`src/features/usage/charts/chartPrimitives.tsx` 一个函数 + 一条单测；
  消费者是 `BarChart.tsx`（近几个窗口、每日 Token 消耗）。**不碰 token、不碰布局。**

**6. 时间轴标签无信息 + 网格线间距无解释**
- 问题：四个刻度全为 `18:00`；网格线间距目测 72–250px 不等；蓝块无标签、贴顶、
  占轨道高 59%；轨道左端一条无说明的 3px 粉红竖线。
- 为什么：scrubber 是日志页的视觉中心（1124×70 的横幅），
  一条读不出信息的坐标轴会让整屏显得「坏掉」，是**性价比最高的单点收益**。
- 怎么改：标签 formatter 按跨度切换——跨度 < 1 分钟用 `18:00:03`，< 1 小时用相对
  秒（`0s / 2s / 5s`）；跨度跨天再回到 `HH:MM`。非线性轴必须在轴上加一个
  「空档已压缩」标记（或把空档画成明确的断口）。蓝块给 tooltip + 占满轨道高
  （或改用 `--chart-1-soft` + 描边，遵守「大填充只允许 -soft」）。粉红竖线要么给图例
  要么删。
- 影响面：scrubber 组件（时间轴 + 轨道）+ 一个 formatter；不动 token。
