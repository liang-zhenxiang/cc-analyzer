# PRD：补齐测试体系（单元 / 端到端 / 真实 GUI）

**父任务**：`10-01-v030-overhaul` · **GitHub Issue**：待建

## 背景

项目现在有一批前端 Vitest 用例（解析、时长、筛选、虚拟化等纯逻辑基础上已覆盖），
但测试网有三个洞：

1. **没有端到端测试**。所有组件测试都在 jsdom 里跑，桥接层是注入的假实现。
   真实的用户流程——选会话 → 看日志 → 筛选 → 出报告——**从来没有被整体跑过**。
2. **没有 GUI 测试**。应用究竟能不能打开、打开后长什么样、
   打包出来的 `.app` 是不是白屏，**全靠人工看一眼**。v0.2.1 那次发布
   Windows 连挂两次，就是因为「本地全绿 ≠ 发布能成」而没有任何自动化兜底。
3. **Rust 侧几乎零测试**。命令层刻意保持薄，但没有测试把「薄」这个约定钉住。

维护者的原话点出了真正的痛点：**「确保后面加的每一个功能都不会影响到老功能」**。
没有这层网，每加一个功能都是一次赌博。

## 期望

### 1. 单元测试补齐

- [ ] 前端：盘点现有覆盖率，补齐**有分支但没断言**的逻辑
- [ ] Rust：给命令层里**可纯函数化**的逻辑补 `#[cfg(test)]` 测试
- [ ] 明确写进规范：**新增功能必须带测试**，解析/时长/筛选/报告的改动必须带夹具用例

### 2. 端到端测试（浏览器层）

- [ ] 用 Playwright 跑真实浏览器，针对 `vite preview` 构建产物
- [ ] Tauri 桥接层用可控的假实现替换（`web/src/api/bridges.ts` 已提供接口抽象）
- [ ] 覆盖关键用户流程：会话列表 → 打开会话 → 日志视图筛选 → 时长树 → 报告面板
- [ ] **接入 CI**，失败时产出截图/trace 供排查

### 3. GUI 测试（真实应用 + 截图）

- [ ] **真实启动打包后的 `.app`**（不是模拟，不是 jsdom）
- [ ] 等待窗口真正渲染完成，**截图存证**
- [ ] 判定「没白屏、关键元素在」至少一条硬断言；截图作为人工复核的证据
- [ ] 产出物（截图）在 CI 里可下载，本地可直接看

### 4. 防回归的机制

- [ ] 三层测试各有明确的**职责边界**，写在 `.trellis/spec/` 里，避免重复覆盖
- [ ] 明确「什么改动必须补哪一层测试」

## 验收标准

- [ ] `npm test` 跑前端单元测试；新增 e2e 与 gui 有各自的入口命令
- [ ] CI 里有对应的 job，且**分支保护只认「CI 总览」**这一条不破
- [ ] GUI 测试能在本机 macOS 上真跑通并留下截图
- [ ] 三个入口都在 `AGENTS.md` 与 `CONTRIBUTING.md` 里写明

## 非目标

- 不追求行覆盖率数字好看。**能发现真实回归**的测试才有价值，
  为了凑覆盖率写的断言不写
- 不在 CI 里跑真机 GUI（macOS runner 的 GUI 能力与成本需实测后再定，
  先保证本地可跑、产物可归档）

## 入手位置

- `web/src/api/bridges.ts` —— 桥接接口抽象，e2e 的注入点
- `web/vitest.setup.ts`、`web/vite.config.ts` —— 现有测试配置
- `web/tests/fixtures/` —— 现有 JSONL 夹具
- `scripts/` —— 新增测试入口脚本
- `.github/workflows/ci.yml` —— 新增 job
- `src-tauri/src/lib.rs` —— Rust 侧待补测试的主体

## 难度

中偏难。GUI 测试是本任务真正的不确定项：Tauri 在 macOS 上没有官方
WebDriver 支持，需要确认可行路径后再定方案。
