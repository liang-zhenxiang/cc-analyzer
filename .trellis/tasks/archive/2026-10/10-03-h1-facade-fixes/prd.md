# PRD：修复门面视觉缺陷（表盘撑爆 / 表格裁切）

> 对应 Round H 子任务 1 · 创建于 2026-10-03
> 发现方式：维护者逐张目验 `gui-artifacts/`（真机取图）与 `docs/screenshots/`（Playwright 归档图）

## 背景

用户提出的本轮第一诉求是「**界面美观度必须是第一位的**」。维护者据此逐张过目了真机与
归档截图，发现两处硬伤——而且其中一处**就挂在项目门面上**。

### 缺陷 1：用量总览的 5 小时计费表盘被撑满整个屏幕

- **证据**：`docs/screenshots/usage-light.png`（Playwright 1440×900）与
  `gui-artifacts/app-window-tab.png`（真机 1400×872）**两张独立来源的图都复现**。
- **现象**：环形表盘直径约 1020px，占满整个内容区，环心读数「68,200」被放大到
  约 90px，副标签「本窗口消耗」同样巨大；KPI 读数行、趋势图等被挤到首屏之外。
- **根因（已定位）**：`chartPrimitives.module.css` 的 `.chart { width: 100% }` 被 `Gauge`
  复用；`Gauge` 作为 `BillingWindowCard.gaugeArea` 这个 `display:flex; flex-wrap:wrap`
  容器的 flex item，`width:100%` 解析为容器宽度，于是独占整行并被等比放大。
  其他图表（BarChart 等）本来就该铺满宽度，所以问题只出在**正方形仪表**上。
- **为什么严重**：这张图是 `README.md` / `README.zh-CN.md` 的**首图**（第 19 / 21 行），
  是潜在用户看到的第一眼。门面挂着破损布局。

### 缺陷 2：会话记录表右端列被裁切

- **证据**：`docs/screenshots/analyzer-log-light.png` 与 `analyzer-log-dark.png`。
- **现象**：表头与每行的最右侧在窗口边缘被硬切，露出一条残缺列（约 x=1405 起），
  既看不到完整列内容，也没有任何「可以横向滚动」的可见提示。macOS 的覆盖式滚动条
  只在滚动时出现，所以静止状态看起来就是「表坏了」。
- **待定位**：需实现者确认是列宽之和超出容器、还是某列 `white-space: nowrap` 撑破
  （`RecordTable`/`LogView` 已在容器上写了 `overflow: auto`，所以更可能是
  「能滚但看不见滚动条 + 首列不粘性」的组合症状）。

### 缺陷 3：视觉验收基线自身在漂

- **证据**：`docs/screenshots/analyzer-empty-light.png`（commit 51cb6f6，10-01）顶栏只有
  两个标签页；`analyzer-log-light.png`（8c8df41，10-02）有三个。**同一目录里的图来自不同
  代码版本**。`usage-dark.png`（cb5116f）里根本没有 `BillingWindowCard`，而更晚的
  `usage-light.png`（03cbde7）里有——同名同批的两张图内容代际不同。
- **后果**：README 与文档引用的是这个目录，贡献者改完视觉也不知道该以哪张为准；
  上一轮「通电」升级后的界面，归档图里有一部分还是升级前的样子。

## 用户故事

- 作为**第一次打开项目页的潜在用户**，我看到的首图应当展示出这个应用真正的样子。
- 作为**应用使用者**，我在用量总览页应当一眼看到完整仪表盘与 KPI 读数，而不是一个
  占满屏幕的巨环。
- 作为**使用者**，记录表的每一列我都应该能读到；若确实放不下，我应该能看出来「可以横向滚动」。
- 作为**贡献者**，我改动视觉后重新出图，得到的应当是一套彼此一致、且与当前代码对应的基线。

## 功能需求

1. **表盘尺寸有界**：`Gauge` 在任何容器宽度下都保持合理的固定尺寸区间
   （设计目标 120–160px 直径），不再随父容器拉伸；宽窗口下读数行应紧临表盘排布，
   而不是被挤到下一行。
2. **表盘不受 `.chart` 通用铺满规则影响**：修复方式必须是「让正方形仪表有自己的尺寸约束」，
   不能靠给 `.chart` 加特例把柱状图/热力图一起改坏——**其他图表当前铺满宽度的行为必须保持不变**。
3. **表格横向可达**：
   - 在 1440px（Playwright 视口）与 1400px（真机窗口）下，**所有列完整可见，不出现残缺列**；
     若列总和确实超出，则必须给出**可见的**横向滚动提示（非覆盖式、静止可见），
     且首列（时间）保持可辨认。
   - 在最小窗口 960×640 下不得出现内容被永久裁切且无法到达的情况。
4. **基线重建**：`docs/screenshots/` 全套图在**同一次运行**中重新生成（6 个视图 ×
   浅/深 × chromium/webkit），彼此代际一致；README 引用的图必须在新套内且内容正确。
5. **基线不再静默漂移**：新增一个自动化检查，使「README 引用了不存在的截图」或
   「截图套缺视图」在本地与 CI 都能被抓住，而不是靠人记得重出图。

## 约束

- 遵守 `tokens.css` 的既有纪律：**不得引入颜色/高度/圆角/时长的字面量**；
  新增尺寸若属通用语义应进 token。
- 不得改动柱状图、热力图、堆叠图、横向条形图的现有视觉（回归风险最高的地方）。
- 三层测试全绿（`npm --prefix web test`、`npm --prefix web run test:e2e`、
  `./scripts/gui-test.sh`、`./scripts/lint.sh`）。
- 真机取图仍需 `gui-capture` feature；`gui-artifacts/` 已 gitignore，不得提交。

## 非目标

- 不做整体视觉重设计（那是 H3 的事）。
- 不为了「塞下列」而删减信息列；列的选择属于产品决策，本轮只修「可达性」。
- 不引入视觉回归截图对比框架（像素 diff）——H2 用真机几何断言解决布局回归，成本更低、噪声更小。

## 验收标准

- [ ] 用量总览页在 1440×900 与 1400×872 下：表盘直径 ≤ 200px 且不超出所在卡片，
      KPI 读数行与趋势图在首屏可见（**以新出的真机截图为准，维护者目验**）
- [ ] 记录表在 1400×872 下无残缺列；若出现横向滚动，滚动条在静止时可见
- [ ] 960×640 最小窗口下两处均可用（无不可达内容）
- [ ] `docs/screenshots/` 全套重出且代际一致（含 `-webkit` 版本），README 双语的图与文字描述相符
- [ ] 新增的截图基线检查在缺图时**会失败**（变异验证：临时删一张图或加一条 README 引用，检查必须报错）
- [ ] 单元测试覆盖表盘的尺寸约束（断言不再依赖 `width:100%` 的通用图表规则）
- [ ] 端到端测试新增断言：在 1440×900 与 960×640 两种视口下，记录表无横向裁切、
      用量总览表盘尺寸在界内
- [ ] CHANGELOG `[Unreleased]` 中文条目（Fixed 分类）
