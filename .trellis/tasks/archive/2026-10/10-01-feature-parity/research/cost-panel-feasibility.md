## 0. 一句话结论

**数据是全的，而且比预期多。**`message.usage` 的四个计数在 **100%** 的 assistant 行上存在，
解析层**已经全部提取**；此外日志里还藏着一份 Claude Code 自己写的**成本快照**
（`type: "cost-state"`），当前解析器完全没读。

**但这个功能不该按调研报告的原方案做。**原因是本机取证出的两条硬事实：

1. 本机 **100% 的流量是第三方路由模型**（deepseek / glm / qwen），**没有任何一个 Anthropic 模型名**。
   按 Anthropic 定价表算，本机没有一条会话能算对。
2. Claude Code 自己的成本快照在本机 **109/120 次都带 `hasUnknownModelCost: true`** ——
   上游自己就承认这些模型的成本它不知道。

**建议：做，但只做「Token 四计数面板 + provenance 徽标」，暂不做金额。**
详见 §7。

### 1.3 解析层现状（精确到行）

`parseJsonl.ts:58-70` 的 `usageOf()` 已提取四个主计数，映射到
`types.ts:4-9` 的 `SessionUsage { inputTokens, outputTokens, cacheCreationTokens, cacheReadTokens }`。

**解析层按 `message.id` 聚合**（`parseJsonl.ts:157-168` 的 `assistantAggregates`，
写入见 `391-436`）——这是一个关键现状：**43282 行 assistant 只对应 16296 个唯一
`message.id`，平均每个 id 被写入 2.66 行**（1 行占 12.6%，2 行占 35.2%，3 行占 44.8%，
最多见到 13 行）。聚合键取 `message.id ?? uuid ?? line-N`。

**聚合时只取首条 usage，后续行不覆盖**（`parseJsonl.ts:394-436`：`existing` 分支只更新
blocks / lineNumbers / timestamp / text，**不碰 `usage`**）。
后文 §2 的实测证明这个「取首条」的近似是可以接受的。

### 1.4 意外发现：`cost-state` 事件（本次调研最重要的发现）

日志里存在 `type: "cost-state"` 的独立事件，**120 条，覆盖 106/241 个文件（44.0%）**，
且 **97/120 位于文件最后一行**（其余分散在文件中，应为周期性快照）。

字段形状（取值统计自 120 条样本）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `totalCostUSD` | float / int | 会话累计美元金额。取证样本区间 0.0000 ~ 946.78 |
| `totalAPIDuration` / `totalAPIDurationWithoutRetries` / `totalToolDuration` / `totalDuration` | int | 已是毫秒级时长，与现有 `duration` 模块口径可直接对照 |
| `totalLinesAdded` / `totalLinesRemoved` | int | 代码行增删 |
| `startTime` | int | |
| `hasUnknownModelCost` | **bool** | **关键字段**，见下 |
| `modelUsage` | dict | **按模型聚合**，见下 |

`modelUsage` 的每个模型条目（共 158 个条目，形状 100% 一致）：

```
inputTokens, outputTokens, thinkingTokens,
cacheReadInputTokens, cacheCreationInputTokens,
webSearchRequests, costUSD
```

**即：Claude Code 自己已经在会话级按模型聚合好了四类 token 和一个美元金额。**

**`hasUnknownModelCost` 的取证结果（决定性）：**

| 取值 | 条数 | 对应 token 量 |
|---|---|---|
| `true` | **109 / 120** | 非零（有真实用量） |
| `false` | 11 / 120 | 全部为 0（空会话） |

**解读：本机凡是真正产生了用量的会话，`hasUnknownModelCost` 一律为 `true`。**
同时 `costUSD` 在这些会话里**仍然是非零的**——说明上游对一个它自己标记为
「模型成本未知」的对象，依然给出了一个金额。

> ⚠️ **该字段的确切语义未确认。**本项目没有 Anthropic 官方文档确认
> `hasUnknownModelCost` 是为「模型名不在定价表中」置位，还是为其他原因。
> 但无论如何，**在上游自己置位 `true` 的情况下把该金额显示为「官方」是不可接受的**。
> 这一点直接决定了 §3 的标签设计。

**当前解析器对该事件的处理**：`parseJsonl.ts:306-311` 把非 user/assistant 的事件
计入 `skippedCounts[type]`，因此 `cost-state` 目前落在 `skippedCounts["cost-state"]` 里，
**数据进来了但被丢掉**，没有任何字段被提取。

### 2.2 实测：本地累加能不能对上官方快照？

这是本次调研**最关键的实验**——它决定「本地估算」这个口径站不站得住。
方法：对 102 个同时含 usage 与 cost-state 的会话，用四种聚合策略计算本地 token 合计，
与快照的 `modelUsage` 合计逐字段比对（纯数字比对，不涉及任何会话内容）。

**策略对比（合计，102 个会话）**

| 策略 | input | output | cache_creation | cache_read |
|---|---|---|---|---|
| **官方快照** | 178,502,426 | 3,621,770 | 8,675,361 | 796,786,835 |
| 去重取首条（≈解析器现状） | 210,751,963 (+18%) | 5,866,128 (+62%) | 3,938,125 (−55%) | 2,281,117,253 (+186%) |
| 去重取末条 | 210,846,473 (+18%) | 5,866,772 (+62%) | 3,938,125 (−55%) | 2,281,119,301 (+186%) |
| 去重取最大值 | 210,846,473 (+18%) | 5,866,772 (+62%) | 3,938,125 (−55%) | 2,281,119,301 (+186%) |
| **不去重直接求和** | 587,767,950 (+229%) | 16,498,154 (+356%) | 10,114,737 (+17%) | 5,785,039,254 (+626%) |

**逐会话看，图景完全不同：**

| 字段 | 会话数 | 中位比值 | p25 | p75 | 最大比值 |
|---|---|---|---|---|---|
| input | 96 | **1.000** | 1.000 | 1.000 | 31.5 |
| output | 96 | **1.000** | 1.000 | 1.000 | 1636 |
| cache_creation | 11 | **0.982** | 0.797 | 1.000 | 1.000 |
| cache_read | 80 | **1.000** | 1.000 | 1.000 | 4,843,853 |

**78 / 102 个会话的四个计数全部落在官方快照 ±2% 以内，中位比值精确等于 1.000。**

**三条可落地的结论：**

1. **必须按 `message.id` 去重。** 不去重直接求和会高估 output 3.5 倍、cache_read 7.3 倍。
   这是最容易踩的坑，而**解析器现状已经是对的**。
2. **取首条 / 末条 / 最大值几乎无差别**（210,751,963 vs 210,846,473，差 0.04%）。
   解析器「取首条不更新」的现状**可以保留，不需要改**。
3. **合计层面的大偏差由极少数会话造成**，不是系统性错误。最极端的一个会话
   本地 cache_read 计 310,006,592，官方快照仅 64。这类离群会话**成因未确认**
   ——可能是快照写入时机早于会话结束、可能是超长上下文的重复计数、也可能是上游本身的缺陷。
   **本报告不对成因下结论。**

> **对功能设计的意义**：本地口径在**绝大多数会话上能对上**，具备可用性；
> 但**存在能差出 4~6 个数量级的个别会话**，且我们无法预先识别哪些会话会出问题。
> 这直接否定了「无差别地展示一个精确到分的金额」的做法（见 §5）。

### 2.3 改动波及面与测试影响

改 `parseJsonl.ts` 的风险最高——该文件 19.5 KB，配套 `parseJsonl.test.ts` 21.8 KB。

**明确会破的**：`cost-state` 从 `skippedCounts` 中消失。任何断言
`skippedCounts` 具体键值（或断言「未识别事件被跳过」）的现有测试都会失败。
**动手前需要先 grep 一遍 `skippedCounts` 的测试断言。**

**不会破的**：`usageOf()` 是纯增量扩展（加字段不改语义），四主计数的现有断言不受影响。

## 3. 口径怎么做才诚实？

### 3.1 核心原则

调研报告要求「每个数字旁挂 `official` / `local_estimate` 标签」。基于 §1.4 和 §2.2 的取证，
**原样照搬这套二分标签在本机数据上会失效**——因为**没有任何一个数字够格叫 `official`**：

- 金额的官方来源只有 `cost-state`，而它在有真实用量的会话上 **100% 带 `hasUnknownModelCost: true`**；
- 本地估算依赖定价表，而本机 **100% 的模型不在 Anthropic 定价表内**。

所以标签体系应当**按「数据从哪来」分级，而不是按「准不准」分级**。
建议四级，**每一级都必须在 UI 上可见，不允许缺省隐藏**：

| 级别 | 标识 | 触发条件 | UI 表现 |
|---|---|---|---|
| **A** | `官方快照` | 存在 `cost-state` **且** `hasUnknownModelCost === false` | 显示金额，徽标「官方快照」。**本机 0 个会话满足** |
| **B** | `官方快照（模型定价未收录）` | 存在 `cost-state` **且** `hasUnknownModelCost === true` | 显示金额，**徽标必须带上 `hasUnknownModelCost` 这个事实**，并附「上游未收录该模型定价」 |
| **C** | `本地估算` | 无 `cost-state`，但有 usage 且**定价表命中该模型** | 显示金额，徽标「本地估算 · 定价表 vX」 |
| **D** | **`未知`** | 无 `cost-state` **且**定价表未命中 | **不显示金额**。显示四个 token 计数 + 一句原因 |

### 3.2 必须标「未知」而不是给个数的情形

以下是**硬规则**，任一命中即不显示金额：

1. **模型名归一化后仍不在定价表内。** 本机的 deepseek / glm / qwen 全部落在这里。
2. **会话内出现多个模型，且其中任一未收录** → 整会话金额标未知。
   只对已收录部分求和并显示「不完整金额」是**更差的选择**——用户会忽略「不完整」三个字。
3. **`model` 为 `<synthetic>`**（本机 50 行）或缺失。
4. **四个计数全为 0**（空会话）。
5. **会话仍在进行中**：无 `cost-state` 且文件 mtime 距当前很近 → 标「会话进行中，成本未结算」。

### 3.3 定价表从哪来

**项目红线禁止联网，因此定价表不能运行时获取。**三个候选方案：

| 方案 | 离线 | 评价 |
|---|---|---|
| **A. 内置静态定价表**（随应用打包的数据文件，含 `version` / `sourceUrl` / `retrievedAt`） | ✅ | **推荐**。但必须显式标注版本与抓取日期 |
| **B. 用户可编辑覆盖**（放在 `appDataDir`，与现有 `meta-cache-v2.json` 同处） | ✅ | **推荐作为 A 的补充**。第三方模型定价只有用户自己知道 |
| **C. 从 `cost-state` 的 `costUSD ÷ tokens` 反推有效单价** | ✅ | **不推荐**。1 个方程 4 个未知数，数学上欠定；只能反推「有效均价」，无法拆分四类计数。若做，只能作为交叉校验，不能作为定价来源 |

**推荐组合：A + B。**定价表以 TypeScript 常量或 JSON 数据文件内置（便于类型检查与 tree-shaking），
用户覆盖存 `appDataDir`。UI 上**任何时候都显示定价表的版本号与来源**。

> **关于第三方模型**：如果要做 deepseek / glm / qwen 的定价，我们必须自己维护一份
> **非 Anthropic 的价目表**，其来源无法通过本项目的离线红线获取，且准确性无从验证。
> 这是本方案最大的诚实性风险点。

### 3.4 缓存读写怎么拆开展示

调研报告特别指出这是用户困惑的来源，取证结果支持这一点：
本机 `cache_read` 合计 **5,784,080,022**，是 `input`（587,767,950）的 **9.8 倍**；
而 `cache_creation` 只有 10,114,737，反而**小于** input。
**四类计数的量级差异达三个数量级**——合并显示会完全掩盖成本结构。

**展示结构（四行 + 一个缩进子行）：**

```
input           输入            588 M
cache_creation  缓存写入        10.1 M
  ├─ 5 分钟 TTL                 … M      ← ephemeral_5m_input_tokens
  └─ 1 小时 TTL                 … M      ← ephemeral_1h_input_tokens
cache_read      缓存读取        5.78 B   ← 通常占比最大，单独一行
output          输出            16.5 M
```

**设计要点：**

1. **四类计数永不合并。**注意现状已有合并发生——`logRows.ts:53-58` 的 `tokensOf()`
   把 `input + cacheCreation + cacheRead` 加在一起当成一个 `input` 用于行级展示。
   **成本面板不应复用 `tokensOf()`**，否则口径立刻违背本建议。
   是否同步修改 `tokensOf()` 需要单独决策（会牵动 `LogView` 的现有列）。
2. **5m/1h TTL 拆分做二级缩进**，不占一级位置。1 小时 TTL 单价显著高于 5 分钟档，
   但取证样本中 `cache_creation > 0` 的仅 816 行，展开频率低，适合折叠。
3. **子对象缺失时按 5 分钟档回退**，并在 UI 上不额外标注（因为缺失 = 该次调用无缓存写入，见 §1.2）。
4. **每行右侧显示占比**（相对四类总和），因为量级差三个数量级，纯数字读不出结构。
5. **不显示「总 token 数」这个单一数字。**它没有语义——把 cache_read 和 output 加在一起不代表任何东西。

## 4. 界面怎么放？

### 4.1 现有信息架构（实测）

- **顶层**：`AppShell.tsx:14` 只有 `analyzer` / `monitor` 两个工作区
  （`WorkspaceTabs.tsx:6`），加一个「设置」按钮开 `ThresholdsPanel`。
- **会话页纵向顺序**（`SessionAnalyzerPage.tsx:277-380`）：
  `SessionHeader` → `SessionList` → `TimelineTrack` → `FilterBar` → 视图切换条
  （日志视图 / 树视图）→ `LogView 或 TreeView` → `ReportPanel`；
  `RecordDetailPanel` 在选中记录时作为右侧栏出现。
- **会话级汇总目前只有一个**：`SessionHeader.tsx:26` 的「总耗时」chip。

### 4.2 落点：两处，都不新增顶层导航

**落点一 —— `SessionHeader` 的成本 chip（主入口，P0）**

在 `SessionHeader.tsx:26` 的「总耗时」chip 之后追加一个「成本」chip，
复用同文件现有的 `.chip` 样式（`SessionHeader.module.css`，已是 `inline-flex` + 边框 +
`--fs-xs` 的胶囊）。

理由：成本与总耗时**同属会话级汇总**，该行已经是会话级摘要的既定位置；
零新增布局、零新增导航、视觉上与现有 chip 完全同构。
chip 内容随 §3.1 分级变化：A/B/C 显示金额 + 徽标，D 显示「成本未知」。

**落点二 —— `CostPanel` 折叠面板（详情，P1）**

新增 `CostPanel.tsx`，插在 `SessionHeader` 与 `TimelineTrack` 之间，**默认折叠**，
由 chip 点击展开。展开后是 §3.4 的四行结构 + 定价表版本 + 每行的 provenance 徽标。

放在这个位置的三个理由：
1. 在 `TimelineTrack` 之上——成本是**会话级**的，时间线是**会话内**的，层级由位置自然表达。
2. 在 `RecordTable` / `LogView` 之外——不打断现有行模型，这是 CC Analyzer 的核心优势。
3. 折叠态几乎不占垂直空间，不影响现有「时间线 + 筛选 + 视图」的主流程高度。

**为什么不放 `ReportPanel`**：`ReportPanel` 是 **AI 生成报告**的容器，
其 `meta` 区（`ReportPanel.tsx:116-126`）里的 `costUsd` 来自 **CLI 的 `total_cost_usd`**
（`report.ts:345`），是**调用 claude CLI 分析时那次调用的成本**，
与会话本身的历史成本是**完全不同的两个数**。放一起会造成严重混淆。
**建议在 `ReportPanel` 的 `meta` 文案里把「成本」改成「本次分析成本」**，与成本面板明确区分。

### 4.3 为什么不新增顶层导航

- `WorkspaceTabs` 只有两项，加第三项会让现有两页的信息密度被稀释。
- 成本是**单个会话的属性**，不是「第三个工作区」。用户不会为了看成本切页。
- 调研报告在 Top 3（导出）明确建议「导出入口放在会话详情与报告页，**不新增顶层导航**」
  ——同一原则适用于成本面板，保持全站一致。

### 4.4 怎么和「时长 / 占比」共存而不打架

| 维度 | 现有 | 新增 | 是否冲突 |
|---|---|---|---|
| 会话级汇总 | `SessionHeader` 总耗时 chip | 成本 chip，**同排紧邻、同视觉规格** | 否，并列 |
| 时间分布 | `TimelineTrack` 时间线 + 时长占比 | 成本是**资源**维度，不在时间轴上 | 否，正交 |
| 行级明细 | `RecordTable` 耗时列 + `tokensOf` | 成本面板**独立计算**，不改行级 | 否 |

**三条避冲突规则：**

1. **不做饼图 / 环形图。**时长占比已经占据了「占比可视化」这个位置。
   两个占比图并排会互相削弱，且色彩语义会撞车（`tokens.css` 的
   `--cat-*` 已承载五类时长语义）。成本占比**只用数字 + 细横条**。
2. **不新增 `--cat-*` 色系。**成本面板用 `--text-secondary` / `--text-tertiary`
   的文字层级表达主次，不用新颜色——符合调研报告 §5「颜色只承担语义，不承担装饰」。
3. **成本 chip 与耗时 chip 之间不加分隔符以外的任何装饰**，
   避免让用户以为两者可以互相换算（它们不能）。

## 5. 风险与不做的理由

### 5.1 会让用户**更不信任**的风险（本功能的主要危险）

按危害排序：

1. **假精确（最危险）。**显示 `$0.4231`，而 §2.2 证明我们已知存在能差出 4~6 个数量级的会话，
   且**无法预先识别**。用户拿这个数去和账单对账，一旦对不上，得到的结论不是
   「这个工具有误差」，而是「这个工具在编数字」——**比不显示数字更糟**。
   精确到小数点后四位的格式本身就构成了一种我们无法兑现的精度承诺。
2. **与官方数字公开冲突。**用户同时看 `/usage` 和本面板，两个数不一致。
   调研报告 §3.1 已经记录了 ccusage Issue #247「工具说还有余量，官方说你已超额」
   正是这个失败模式。**我们要避免成为第二个 ccusage。**
3. **定价表静默过期。**内置表在模型调价后不再正确，而用户不会知道表是旧的。
   这是**长期、无声、累积**的错误。
4. **第三方模型定价的来源不可靠。**本机 100% 流量是 deepseek / glm / qwen。
   为它们维护价目表意味着我们要对外宣称一个**无法从本机验证**的价格。
   这与「数据不出本机」的定位存在张力——我们没有权威来源。
5. **`hasUnknownModelCost` 的语义未确认。**我们猜它意味着「模型未收录」，
   但也可能意味着别的。**基于未确认的语义去设计标签，是在用一个猜测支撑一个信任承诺。**

### 5.2 宁可怎么处理

**核心取舍：宁可只给事实，不给估算。**

- **Token 计数是「读出来的事实」，不是估算。**它 100% 存在、直接来自日志、
  不需要任何外部输入、几乎不可能错。**把它做好，就已经回应了「数字可信吗」的核心焦虑。**
- **金额是「算出来的推断」。**在定价表命中率 = 0 的现状下，它只会引入新的不确定性。
- 因此：**宁可不显示金额，也不显示一个我们无法标注来源的金额。**
  §3.1 的 D 级（显示「成本未知」+ 四个计数）**不是降级方案，而是当前条件下的正确输出。**

**「我们不编数」本身就是一个产品信号。**调研报告 §3.1 的结论是用户要的不是更多数字，
而是「这个数字可信吗、它从哪来」。一个在算不出来时**坦率显示「未知」**的面板，
比一个永远给出四位小数的面板，更直接地兑现了这个承诺。

### 5.3 其他风险

- **`parseJsonl.ts` 是核心路径**，21.8 KB 测试守着。`cost-state` 提取会改
  `skippedCounts` 行为，需先排查受影响的断言（见 §2.3）。
- **性能**：`cost-state` 每文件最多几条，提取成本可忽略；
  但 §3.4 的四类计数聚合需要遍历全部 assistant 记录，应在 `ParsedSession` 上**一次性算好**，
  不要在 render 里循环。
- **会话进行中**：`cost-state` 只在 44% 的文件里出现且多为最后一行，
  进行中的会话大概率没有快照 → 必须有「进行中，未结算」态（§3.2 第 5 条）。

## 7. 建议：做，但只做阶段一

### 阶段一（**建议立即做**）：Token 四计数面板 + provenance 徽标

**范围**：只做 §3.4 的四类计数展示 + §3.1 的 D 级「未知」态 + 完整提取
`cache_creation` 的 5m/1h 拆分。**不做任何金额。**

**理由**：
- **数据 100% 可靠**——直接读日志，不依赖任何外部输入，不需要定价表，不涉及联网。
- **直接回应最强用户信号**——调研报告 §3.1 的结论是用户要的是「这数字可信吗、从哪来」，
  而不是更多数字。一个**明确标注来源、算不出来就说未知**的面板就是答案。
- **实现成本低、风险可控**——不碰定价表这个最大的不确定性来源。
- **是阶段二的必要前置**——四类计数的正确提取与展示，是任何金额计算的基础。

**验收标准**：能在一个会话上正确显示四类计数与 5m/1h 拆分；
在模型未收录时明确显示「成本未知 · 未收录该模型定价」而**不是 0 或空白**。

### 阶段二（**暂缓**）：金额

**前置条件（缺一不可）**：

1. **查清 §2.2 中离群会话的成因**——在本地口径能稳定对上官方快照之前，
   任何金额都是不可靠的。这是**技术前置**。
2. **确定第三方模型的定价来源**。若无法给出可靠来源，
   则本机场景下金额功能**永远停留在 D 级（未知）**，此时阶段的收益为零。
   这是**产品前置**。
3. **确认 `hasUnknownModelCost` 的确切语义**（§1.4）。这是**口径前置**。

**结论**：阶段一的价值不依赖阶段二，而阶段二的三个前置条件目前**一个都不满足**。
**不要为了「成本面板」这个名字而去实现一个我们无法为其准确性负责的数字。**
