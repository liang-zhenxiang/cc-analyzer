# PRD：竞品对齐与功能增强

**父任务**：`10-01-v030-overhaul` · **GitHub Issue**：待建

## 背景

维护者的要求里有两条关键约束：

> 「你必须想象该项目如何打造才能吸引更多的人来使用该项目」
> 「你可以自行检索其他类似的项目，对比跟他们的差异，将优秀的内容添加到我们这边，
> 当然不能一昧复制，要经过融合改造无缝融合进来」

这个品类的工具（Claude Code 会话分析 / LLM 可观测性 / 时间线可视化）已经有不少
成熟实现。闭门造车有两个风险：做出别人早就有的功能（浪费），
或者漏掉用户已经形成预期的必备功能（劝退）。

## 期望

### 1. 调研要有据可查

- [ ] 调研同类工具，**记录可追溯的来源**（仓库、Issue、讨论）
- [ ] 每条结论区分「我确认的」与「我推测的」——推测的标注清楚
- [ ] 重点找**真实用户抱怨**，而不是功能清单对比

### 2. 提炼优先级

- [ ] 按「价值 ÷ 实现成本」排序，给出明确的前 N 项建议
- [ ] 每项要说明：**为什么适合这个项目**（而不是「别人有所以我们要有」）
- [ ] 明确列出**决定不做**的项及理由

### 3. 融合落地

- [ ] 借鉴的功能必须**改造后并入现有信息架构**，不是加一个平行的新页面
- [ ] 新增功能要带测试（承接 `10-01-testing-infra` 的约定）
- [ ] 用户可感知的改动记入 `CHANGELOG.md` 的 `[Unreleased]`

## 验收标准

- [ ] 调研结论有来源、有取舍、有优先级
- [ ] 落地的功能至少覆盖调研中的**高价值项**，且每个都有测试
- [ ] 没有引入与现有设计语言冲突的界面

## 非目标

- **不做功能堆砌**。维护者把美观度排在功能数量之前——
  候选功能如果做不精致，宁可不做
- 不照抄交互。同类工具的设计选择有其自身上下文，
  直接搬过来往往与我们的信息架构冲突

## 入手位置

- 调研：外部（WebSearch / WebFetch）
- 落地：`web/src/features/`、`web/src/app/`
- 记录：本任务目录的 `research/`

## 难度

中等。调研本身不难，**难在克制**——候选清单会很诱人，
但每一项都要占用界面空间与维护成本。

## 备注

调研结论必须落进本任务的 `research/` 目录，不能只留在会话里。
这是维护者明确要求的「沉淀」。
