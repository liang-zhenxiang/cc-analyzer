# 协作流程：Trellis 与本项目既有流程的融合

> 本文只回答一个问题：**Trellis 引入之后，两套流程怎么协同。**
> 其余主题各有唯一权威位置，见文末「权威分工表」——改规则时只改权威那一处，
> 不要在多个文件里各写一份。

---

## 为什么是融合，不是二选一

本项目原本有一套流程（写在 `AGENTS.md` 与 `.claude/skills/maintain-loop/`）：
以 GitHub Issue / PR / CI / Release 为载体，围绕**一个版本**展开。

Trellis 带来的是另一套：以 `.trellis/tasks/` 为载体，围绕**一个任务**展开。

两者不是竞争关系，而是**不同粒度**：

| | 管什么 | 载体 |
| --- | --- | --- |
| Trellis | 一个任务**内部**怎么想清楚、怎么做完 | `.trellis/tasks/<task>/` |
| 本项目既有流程 | 任务**之间**怎么流转、怎么上车、怎么发版 | GitHub Issue / PR / Release |

硬要二选一会各丢一半价值。只用 Trellis：产物进不了 CI 门禁和发布流水线，
规划得再漂亮也发不出去；只用既有那套：需求探索的过程留在会话里，
会话一压缩就没了，下一个接手的人只看得到结果、看不到取舍。

---

## 粒度对应关系

| Trellis 阶段 | 本项目对应的动作 |
| --- | --- |
| **Phase 1 Plan** — `prd.md`（`design.md` / `implement.md` 用于复杂任务） | 对应 GitHub Issue 的「背景 / 期望 / 入手位置 / 难度」四段。复杂任务额外落 `design.md` 与 `implement.md` |
| **Phase 2 Execute** — `trellis-implement` → `trellis-check` | 在 `feat/*` 分支上实现；`trellis-check` 要跑的东西与我们的「提交前检查」是同一套：`./scripts/lint.sh` + 前端测试 + Rust 三件套 |
| **Phase 3 Finish** — 更新 spec → 提交 | 更新 `CHANGELOG.md` 的 `[Unreleased]` → 提交 → 开 PR → **CI 全绿** → squash 合并 |
| —— | **发布**：Trellis 不管发布，仍走既有的 `chore/release-vX.Y.Z` 流程 |

**关键分歧点：Trellis 的 Finish 不等于发布。**
任务收尾到「PR 已合并」为止。发布是独立的一轮，由 tag 触发，
节奏由维护者决定——不要让每个任务都触发一次发版。

---

## 任务制度：新功能一律走 Trellis 流程

**这是硬规则，不是建议**：往后**每一个新功能的开发都走 Trellis 流程**。
不存在「这次先跳过、下次补上」——跳过的那次就是流程失效的地方。

| 情形 | 怎么做 |
| --- | --- |
| **新功能**（用户可感知的能力增删改） | **必须**建任务：`prd.md` →（复杂时加 `design.md` / `implement.md`）→ `task.py start` → 实现 → 检查 → 更新 spec → 提交 |
| 缺陷修复、重构、测试补充 | 建任务；规模很小的可以直接改，但**要在提交信息里说清为什么不建** |
| 需要先调研/选型再动手 | 建任务，结论写进任务目录的 `research/` |
| 纯答疑、纯解释、不落盘 | 不建 |
| 改错别字、改一个常量 | 不建，直接改 |

Trellis 的默认行为是「每次动手前先问要不要建任务」。本项目**已经预先授权**，
所以按上表自行决定，**不要再问**。

**一个 GitHub Issue 对应一个 Trellis 任务**，两者标题对齐。这不是形式主义：
Issue 是给协作者看的门面，任务目录是自己用的工作台——
PRD 里的取舍、调研笔记、被否掉的方案放在工作台，不往 Issue 里堆。

任务完成后用 `/trellis:finish-work` 归档；
归档前确认 `CHANGELOG.md` 已更新、PR 已合并。

> **为什么要把这条写死**：规范一旦变成「看情况」，就总有不用的理由；
> 而不用 Trellis 的那次，规划不会落盘、检查没有记录，
> 下一个人接手时看到的就是「结果在、为什么不在」。这正是引入 Trellis 要解决的病。

## 分工：主会话做调度与验收，实现交给子 agent

**这是硬规则**：每一个任务的开发，主会话只承担两个角色——**调度者**与**验收者**。
功能的实现**一律由智能体团队里的子 agent 完成，主会话不自己写实现代码**。

### 为什么

三条，都不是形式主义：

1. **上下文经济**。实现过程会产生大量过程性细节（试错、反复读文件、改了又改），
   这些留在主会话里会挤掉真正需要长期持有的东西——需求、红线、全局状态。
   子 agent 在自己的上下文里消化掉过程，只把结论交回来。
2. **验收必须是独立的**。「实现的人自己说没问题」不构成验收。
   主会话不参与实现，才天然站在一个独立的位置上。
   这是验收有效性的前提，不是流程装饰。
3. **可并行**。互不依赖的子任务同时派发，主会话负责编排与汇总。

### 边界

| 主会话（调度 + 验收） | 子 agent（实现） |
| --- | --- |
| 拆解任务、写 `prd.md` / `design.md` / `implement.md` | 按 PRD 写实现 |
| 定范围、定取舍、定验收标准 | 补测试、跑本地检查 |
| 派发子任务，带上上下文与约束 | 调研、对比、给方案建议 |
| **独立核实**子 agent 的结论与产物 | 汇报做了什么、怎么验证的 |
| 合并、发版、写 CHANGELOG | —— |

**主会话仍然亲自做**：读代码以形成判断、跑验收命令、审 diff、做合并决定，
以及那些**必须由验收者本人完成**的事——例如亲自看截图、亲自复现缺陷。
「派 agent 去看一眼」不算看过。

### 派发时要给什么

子 agent **看不到主会话的上下文**，所以派发提示必须自包含：

- **任务**：要做什么，一句话说清
- **依据**：PRD / spec / Issue 的**路径**，让它自己去读——不要把全文贴进去
- **约束**：项目红线里与本次相关的那些（数据不出本机、不提交产物……）
- **产出**：写哪些文件、写到什么程度
- **验证方式**：它自己要跑什么命令来证明做对了

Trellis 的约定是派发提示以 `Active task: <task.py current 给出的路径>` 开头。

### 验收不是复述

**子 agent 说「已完成、测试通过」，不等于验收通过。** 验收者必须自己：

- 跑一遍它声称跑过的命令，或者读 CI 的真实结果
- 看它声称产出的东西——文件真的在吗？内容真的对吗？截图真的是那个样子吗？
- 对着 **PRD 的验收标准**逐条核对，而不是对着它的总结核对

本项目已经有过教训：一个子 agent 写的规范里留着「`@types/node` 故意未安装」，
而当时我们已经装了。**它没有撒谎，只是它的世界已经过时了。**
唯一可靠的办法是自己去看。

## 与本项目红线的交界

Trellis 的部分默认行为**必须让位于本项目红线**（红线全文见 `AGENTS.md`
「项目红线」一节，那是唯一权威）。两处需要特别说明：

- **Trellis 的 journal 自动提交**（`session_auto_commit`）默认开启，
  会自行 `git add` + `git commit`。本项目的提交信息受 CI 校验
  （Conventional Commits），且提交必须能追溯到 Issue——
  所以**只用它记录 `.trellis/workspace/` 下的日志**，
  不要把业务改动交给它提交。
- **`.trellis/scripts/` 与 `.claude/hooks/` 是被自动执行的代码**
  （SessionStart / UserPromptSubmit / PreToolUse）。
  改动这两处等同于改动会在每次会话静默运行的代码，
  必须按 `SECURITY.md` 的说明走审查，不能当作普通文档改动。
- **`.trellis/spec/` 只留本项目的规范**。Trellis 自带的两份通用思考指南
  （`cross-layer-thinking-guide.md`、`code-reuse-thinking-guide.md`）已被删除——
  它们举的例子是 **Trellis 自身代码库**的（模板注册表、`getAllScripts()`、
  多平台分支），与 CC Analyzer 无关，留着会让人误以为那是本项目的约定。
  **`trellis update` 有可能把它们再放回来**：看到就删，
  判断标准是「它举的例子是不是本项目的代码」。

**为什么要有这张表**：同一个主题写在两个地方，两份就会漂移；
漂移的规则比没有规则更危险，因为它让人按错误的前提行动。
新增规则前先查这张表——**能挂到已有权威位置的就挂过去，不要新起一份**。

## 常见误用

- **把 Trellis 任务当 Issue 用**：任务目录不入 PR 讨论，Issue 里也不抄 PRD 全文。
  两者各有读者，重复维护必然漂移。
- **每个任务都发一次版**：发布是版本级的动作，不是任务级的。
  多个任务合并进一个 `[Unreleased]`，攒够了再发。
- **绕过 CI 直接合并**：Trellis 的 `trellis-check` 是本地自检，
  **不能替代 CI**。分支保护只认「CI 总览」这一个 check。
- **在 `.trellis/spec/` 里重抄 AGENTS.md**：规范要引用，不要复制。
