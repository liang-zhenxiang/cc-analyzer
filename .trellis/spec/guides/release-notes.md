# 发布说明（Release Notes）

> **本文是「发布说明长什么样」这一主题的唯一权威位置。** 发布**步骤**（切分支、
> 版本号三处同步、推 tag）仍归 [`docs/MAINTAINER_GUIDE.md`](../../../docs/MAINTAINER_GUIDE.md)，
> 本文只管**说明本身**：写什么语言（含 CHANGELOG 条目该用什么语言）、由谁生成、
> 坏了怎么办。要改规则改这里，别在别处再写一份——漂移的规则比没有规则更危险。
>
> 一句话版本：**发布说明必须全中文；`CHANGELOG.md` 的段落会被原样拼进发布说明，
> 所以它的新条目也必须是中文。**

---

## 条款一：发布说明**必须全中文**

面向中文用户，没有英文版，**也不要加**。这是维护者的明确选择，不是「暂时没做」：

- README 有中英双份，是因为它面向还没决定要不要用的人；
  发布说明面向已经在用的人，他们读的是中文。
- 不做英文版还有一个更硬的理由：**多一份就多一份会漂移的文本**。
  同一件事写两遍，改的时候只改一处，另一处就成了错误信息。

### 判据一：不出现英文模板串

这些是**机器生成的固定串**，由
[`scripts/format-release-notes.sh`](../../../scripts/format-release-notes.sh) 转换：

| 英文 | 中文 | 来自 |
| --- | --- | --- |
| `## What's Changed` | `## 变更清单` | GitHub 模板（常量，配置改不了） |
| `## New Contributors` | `## 新贡献者` | 同上 |
| `**Full Changelog**: <url>` | `**完整变更记录**：<url>` | 同上 |
| `* 描述 by @user in <url>` | `* 描述（@user 提交于 <url>）` | 同上 |
| `* @user made their first contribution in <url>` | `* @user 的首次贡献：<url>` | 同上 |
| `### Added` / `Changed` / `Deprecated` / `Removed` / `Fixed` / `Security` | `### 新增` / `变更` / `弃用` / `移除` / `修复` / `安全` | **CHANGELOG 段**（见下一节） |

六个分类标题**不在 `CHANGELOG.md` 里改**：那是 Keep a Changelog 的标准英文分类，
`AGENTS.md` 规定分类固定为它们、不许自创——保持原样是给协作者看的，
中文只在拼进发布说明时出现。

PR 清单里 `###` 那一层的分类标题**不靠这张表**，由
[`.github/release.yml`](../../../.github/release.yml) 直接配成中文——
配置能解决的就不靠后处理猜，猜错是静默的。

### 由条款一直接推出：CHANGELOG 的新条目也用中文写

**这一条是「全中文」里最容易漏的一半**，因为它的因果不在发布流程里，
而在拼接方式上：

> `release.yml` 的组装步骤把 `CHANGELOG.md` 中该版本的段落**原样**拼进发布说明
> （`./scripts/format-release-notes.sh changelog-section.md >> release-notes.md`）。
> 也就是说，**CHANGELOG 段落是发布说明的子串**——
> 「CHANGELOG 用英文、发布说明用中文」不是两种风格的选择，而是**不可能并存**：
> 前者怎么写，后者就长什么样。脚本只能换掉六个分类标题，正文它一个字都不动。

因此 **`CHANGELOG.md` 的新增条目一律用中文书写**，`[Unreleased]` 与未来的
`[X.Y.Z]` 都是。它是写给使用者看的发布说明正文，不是内部工程日志。

**既有历史条目（`[0.3.0]` 及更早）不要回改。** 那是**已发布版本**的记录，
发布页上当时挂的就是那些文字；回改会让「那次发布说明到底长什么样」不可考，
也会让 `CHANGELOG.md` 的 diff 里混进与本次改动无关的大量噪音。
这条规则**从写下的那一刻起往后生效**，不溯及既往。

> 顺带一提，`CHANGELOG.md` 的 `[Unreleased]` 段目前在这一点上还没有对齐
> （条目是英文的）。它不属于「历史条目」——它还没发布过，**下次发版前应当
> 改写成中文**，否则那个版本的发布说明会是英文的。

## 三段式：语言正确性不能押在任何一段身上

发布说明由三段拼装，每段**各自独立降级**——任一缺失都不阻断发布：

| 段 | 来源 | 语言从哪来 |
| --- | --- | --- |
| ① 摘要（可选） | Claude API，未配 `ANTHROPIC_API_KEY` 时整段跳过 | prompt 直接要求输出中文 |
| ② 变更内容 | `CHANGELOG.md` 里本版本的手写段，**原样拼入** | **人写的**——条款一第二节管的就是这里 |
| ③ 变更清单 | `releases/generate-notes`（PR 列表 / 贡献者 / 对比链接） | 见下 |

第三段是唯一整段由机器生成的地方，拆成两层解决：

- **`### 分类标题`** 由仓库级 [`.github/release.yml`](../../../.github/release.yml)
  提供中文标题。分类是**按 PR 标签**匹配的（GitHub 只支持标签，不支持按提交
  前缀匹配），标签由 `.github/labeler.yml` 按改动路径自动打。
  `labels: ['*']` 的通配必须放最后：一个 PR 归入**第一个命中**的分类，
  少了通配，未匹配的 PR 会从发布说明里静默消失。
- **`## What's Changed` / `## New Contributors` / `**Full Changelog**`**
  是 GitHub 模板里的常量，任何配置都改不了，只能事后转换——
  由 [`scripts/format-release-notes.sh`](../../../scripts/format-release-notes.sh)
  完成，`release.yml` 的「组装发布说明」步骤调用它。

> **刻意不走「先生成英文再让 AI 翻译」这条路。** AI 摘要那一步本来就是可选的，
> 把语言正确性押在它身上，等于「没配 API Key 的发布退回英文」——
> 一个只在特定环境下才成立的正确性，不是正确性。

### 转换脚本的约定

- 输入：`generate-notes` 的原始正文**或 CHANGELOG 的手写段**（文件或 stdin）；
  输出：中文（stdout）
- `--check <文件>`：只检查不转换，查到英文固定串就打印命中行并以 **1** 退出
- 退出码：转换模式下内容为空/缺段一律 **0**（降级不阻断发布）；
  参数错误或输入文件不存在是 **2**（那是调用方的 bug，不能伪装成「这次没有 PR」）
- **幂等**：输出再喂回去一次结果不变。tag 被重复推送会触发第二次发布工作流，
  走 `gh release edit` 分支，不幂等的转换会把已中文化的说明再改一遍
- 只做上面那张表里的固定串；**不猜**任何东西——猜错是静默的

> **`--check` 只能证伪，不能证成。** 它认的是英文**模板串与分类标题**；
> 一段英文**正文**（比如 CHANGELOG 里没改成中文的条目）它一个字都看不出来——
> 「用正则判断一段话是不是英文」不是正则该干的事。所以「CHANGELOG 条目用中文」
> 那条靠人守，不靠这道检查。

## 验证方式

转换逻辑**不许只写在 `release.yml` 的 `run:` 里**：那样唯一的验证方式就是
「发一次版，用人眼看」，而发布是对用户可见、且要重发才能改的动作。

| 层 | 位置 | 跑法 |
| --- | --- | --- |
| 脚本自测（夹具逐字比对 + 幂等 + 无英文残留） | [`scripts/format-release-notes-test.sh`](../../../scripts/format-release-notes-test.sh) | `./scripts/format-release-notes-test.sh` |
| 夹具 | `scripts/tests/fixtures/release-notes/*.in.md` / `*.expected.md` | —— |
| CI | `.github/workflows/ci.yml` 的 `release-notes-test` job | 自动 |
| 组装后的兜底告警 | `release.yml` 组装步骤末尾 `format-release-notes.sh --check` | 自动（只警告） |

夹具里的 `.expected.md` 是**人工核对后写下的**，不是脚本生成的快照——
自己生成的快照会让「脚本坏了」与「预期变了」长得一模一样。
新增一种输入形态就加一对夹具，并在自测脚本的用例清单里登记
（两者不一致时脚本会红，防止「夹具加了但从来没被跑过」）。

`release.yml` 里另有一道**兜底告警**：组装完成后跑一次 `--check`，仍有英文模板串
就打 `::warning::` 并把命中行打出来。**只警告不失败**——三段式各自的降级是既有
设计，措辞不完美也好过整次发布卡住。检测式**只有脚本里那一份**，
工作流不另抄正则（抄的那份不会跟着改）。

## 常见误用

- **加英文版**：这是明确不要的，理由见条款一。
- **改分类标题却只改了 `release.yml` 的文档**：分类在
  [`.github/release.yml`](../../../.github/release.yml)，不在工作流里。
- **以为改完本地的 `.github/release.yml` 就生效**：`generate-notes` 是**从远端
  默认分支**读这个文件的（不是本地工作区、也不是当前 tag）。文件不在 `main` 上时
  API 直接返回 400，工作流的降级分支会把**整份 PR 清单**丢掉，只剩一句警告。
  改完这个文件要先合进 `main` 再发版。
- **看到英文串就去脚本里加模糊匹配**：先确认是不是 `release.yml` 没生效
  （标签缺失会让 PR 落到「其他变更」），配置能解决的就不要靠后处理猜。
- **改完转换规则不更新夹具**：自测会红，但更糟的是有人「顺手」把
  `.expected.md` 按实际输出重写一遍——那正好把回归写进了预期里。
- **以为「CHANGELOG 写英文、发布说明反正会中文化」**：不会。CHANGELOG 段落是
  原样拼进去的，脚本只换六个分类标题。见条款一的第二节。
- **回改历史版本的 CHANGELOG 条目**：`[0.3.0]` 及更早是已发布版本的记录，
  改了就等于篡改发布历史。规则从写下时起往后生效。
- **拿 `--check` 当「全中文」的验收**：它只认模板串与分类标题，认不出英文正文。
