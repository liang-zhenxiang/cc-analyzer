# Security & Permissions

> The Tauri 2 ACL model as this project actually uses it, plus the path and
> process rules that the ACL does **not** enforce.

---

## The Permission Model

Tauri 2 is deny-by-default: a registered command is unreachable from the webview
unless a capability grants it.

- `src-tauri/capabilities/default.json` is the only capability. It is bound to
  `"windows": ["main"]` and lists every granted permission by identifier.
- App-level commands use bare identifiers (`allow-read-dir`, `allow-run-lines`);
  plugin commands are namespaced (`dialog:default`, `float:allow-enter`).
- The `allow-*` identifiers resolve to
  `src-tauri/permissions/autogenerated/<command>.toml`, generated by
  `tauri-build` from the command list in `build.rs`.
- Currently granted: 13 app commands, `float:allow-enter` / `float:allow-exit`,
  and `core:default` / `core:event:default` / `core:window:default` / `dialog:default`.

Wiring a new command into this model is [command-guidelines.md](./command-guidelines.md)
steps 3–5. **Never** add a permission, scope, or capability without saying in the
PR why the command needs it (AGENTS.md §Security & Configuration Tips).

---

## The ACL Does Not Constrain Arguments

Every generated file says `"Enables the <cmd> command without any pre-configured
scope."` There is no `scope` block anywhere in `permissions/`, so the capability
list is a *switch*, not a sandbox:

- `read_text`, `read_head`, `write_text`, `read_dir`, `stat` accept **any
  absolute path** the OS account can reach.
- `run_lines` and `spawn_detached` accept **any program and arguments**.

The only thing standing between crafted session content and the filesystem is
frontend-side validation — which is why the next section matters.
`docs/ARCHITECTURE.md` states the same contract: "路径校验在前端调用侧负责".

## Path Validation Rules

Anything derived from session content is untrusted input: Claude Code JSONL files
name their own sub-session paths, so a hand-crafted file can try to make the app
read an arbitrary path.

- Sub-session paths are checked with `isPathInside` / `isPathInsideAny`
  (`web/src/lib/path.ts:60`), which resolve `.` and `..` **before** comparing
  segments so scoping cannot be tricked by traversal. Call sites:
  `web/src/features/sessions/sessionGraph.ts:367` and
  `web/src/features/sessions/RecordDetailPanel.tsx:45`.
- The comment on `isPathInside` is the norm to follow: it names the threat
  ("a crafted JSONL must not make the app read a file outside the session tree"),
  not just the mechanics.
- The **only** trusted source of an arbitrary external path is a path the user
  picked themselves: `import_session_menu` (lib.rs:483) opens the native dialog
  and emits `session:import`; the frontend then reads that path.
- Paths the app writes by itself go to `app_data_dir` (`meta-cache-v2.json`) —
  keep it that way; do not write caches next to user files.

If you add a path-taking command **and** the path can come from session content,
add the containment check on the calling side and say so in the PR. Do not
assume the ACL protects you.

## Process Spawning

- Commands take `cmd: String` + `args: Vec<String>` as a separate argv — never a
  single shell string. Do not add a `shell(command)` command.
- `child_command` (lib.rs:71) has one documented exception: on Windows,
  extension-less programs are routed through `cmd.exe /d /c` because
  npm-installed CLIs are `.cmd` shims that `CreateProcess` cannot spawn
  directly. It also sets `CREATE_NO_WINDOW`. Keep the comment explaining why.
- `spawn_detached` (`process_group(0)` on Unix, null stdio) backs the frontend's
  `openFolder` (`open` / `explorer` / `xdg-open`) and `openClaudeTerminal`.
- `openClaudeTerminal` (`web/src/api/tauri.ts:60`) interpolates the session id
  into an `osascript` / `sh`-style argument string, guarded by a UUID regex:
  `/^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i`.
  **This guard is load-bearing** — without it the session id is a command
  injection vector. Never relax it, and never route a raw session title or path
  through the same call.

## Webview and Configuration Notes

- `tauri.conf.json` sets `app.security.csp` to `null`: there is **no
  Content-Security-Policy backstop**. Combined with unscoped `run_lines` and
  `write_text`, any script execution inside the webview is equivalent to
  arbitrary command execution. Treat rendering untrusted session content as
  security-relevant and keep explicit guards instead of trusting the platform.
- The `float` plugin declares `DefaultPermissionRule::AllowAllCommands` in
  `build.rs`, but the capability grants its two commands explicitly and never
  references `float:default` — the rule is inert. Don't start referencing it.
- Session data, user paths, and conversation content never leave the machine.
  The app ships no telemetry; the only network call is `monitor_ping` (TCP to
  `127.0.0.1:8090`).

## Current Gaps (known, not yet fixed)

Recorded so future changes don't mistake them for guarantees:

1. `cancel_lines` is missing from `app_manifest.commands` in `build.rs`; its
   permission file survives only because `tauri-build` never prunes that
   directory. Fix: add `"cancel_lines"` to the manifest.
2. `write_text` creates missing parent directories (`create_dir_all`) and writes
   anywhere — a privileged primitive reachable by any code in the webview.
3. `read_head`'s `max_bytes` is caller-supplied and unbounded, and `read_text`
   reads a whole file into memory — a buggy caller can force a large allocation.
4. `exec_text` has no `timeout_ms` and no cancel handle: if the child hangs,
   `command.output().await` never resolves and nothing can stop it — use
   `run_lines` when the caller may need to abort.
